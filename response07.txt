## Qué hace QueryDapperRegex()

Es una query Dapper **síncrona y bloqueante** que ejecuta directamente sobre el objeto `IDbConnection`. No usa `QueryAsync`. El thread que la invoca queda bloqueado hasta que SQL Server responde o hasta que la conexión lanza una excepción.

`connectionString` es resuelto en Program.cs vía `EnvironmentDetector` (clave `"DIExtractDB"`), con fallback a `appsettings`:

## Apertura y cierre de la conexión

ConnectionProvider.cs:

```csharp
private void Create()
{
    lock (this)                                        // ← lock compartido
    {
        if (_connection == null || !_connection.State.Equals(ConnectionState.Open))
        {
            _connection = provider(connectionString);
            _connection.Open();                        // ← síncrono, hasta 30 s
        }
    }
}
```

La conexión se cierra vía `.Exec(dBConnectionHandler.Dispose)` al final de la cadena railway. `Dispose()` hace `Close()` + `Dispose()` + `_connection = null`. Correcto en el flujo normal.

**Pero**: si `_connection.Open()` lanza una excepción (fatal error) o tarda 30 segundos, **todos los threads que estén esperando el `lock` permanecen bloqueados** durante ese tiempo.

## Reutilización incorrecta de la conexión

`ConnectionProvider` instanciado en `BootRegexCalls` es único: está dentro de `RegexValidations` que es registrado como **Singleton** en Program.cs:

```csharp
builder.Services.AddSingleton(x => x.GetRequiredService<IBootable>().BootRegexCalls(connectionString));
```

Esto significa:
- **Un solo `ConnectionProvider`** para toda la aplicación.
- **Un solo `_connection`** compartido entre todos los requests concurrentes.
- **Un solo `lock(this)`** que serializa todos los accesos.

Cuando la conexión falla y se está intentando reabrirla, **TODOS los threads concurrentes quedan apilados esperando ese lock**.

---

## Operación síncrona y bloqueo de threads

Confirmado: **100% síncrono y bloqueante**.

- `_connection.Open()` — síncrono, bloquea hasta `Connect Timeout=30` s
- `Connection().Query<>()` — Dapper síncrono, bloquea hasta que SQL responde
- `lock(this)` — serializa todas las llamadas concurrentes

Cuando SQL Server tiene un fatal error o está degradado:
1. Thread A entra al `lock`, llama `_connection.Open()`, espera hasta 30 s
2. Threads B, C, D, ... están bloqueados en `lock(this)`, inactivos
3. Cada uno de esos threads proviene del Thread Pool de Kestrel

## Cómo puede bloquear /health/liveness

El mecanismo confirmado por el código:

```
Timer de 15 min invalida _regex → _regex vacío
       ↓
Múltiples usuarios en /Verify → OnAfterRenderAsync → ReadRegexBase()
       ↓
CallDB() → QueryRegexBase() → EstablishConnection() → Create()
       ↓
lock(this) [ConnectionProvider compartido — Singleton]
       ↓
_connection.Open() → "Internal connection fatal error" / SQL Server degradado
       ↓
Thread bloqueado en _connection.Open() hasta Connect Timeout = 30 segundos
       ↓
Todos los demás threads bloqueados en lock(this), esperando
       ↓
Thread Pool de Kestrel agotado
       ↓
GET /health/liveness ingresa → no hay threads disponibles
       ↓
Kestrel acepta el TCP pero no puede procesar la request
       ↓
K8s probe: "context deadline exceeded" → pod reiniciado
```

## HECHOS CONFIRMADOS

1. **`QueryDapperRegex()` (línea 37)** ejecuta `dBConnectionHandler.Connection().Query<RegexDapperRecord>(_sqlRegexRead)` — Dapper síncrono sobre `DIGlobalSetting` en `DIExtract`@`LWVTDBSQLA007`.

2. **`QueryRegexBase()` (línea 22)** llama a `EstablishConnection()` → `Create()` que tiene un `lock(this)` alrededor de `_connection.Open()`. El timeout de conexión es **30 segundos**.

3. **`IRegexValidationMemo` es Singleton** — un único `ConnectionProvider` compartido entre todos los circuits/users. El `lock(this)` serializa todos los accesos concurrentes al mismo objeto.

4. **La query SQL se ejecuta en el thread del caller, sin async, sin `await`**. Bloquea el thread hasta que SQL responde.

5. **El único caller es Index.razor `OnAfterRenderAsync`**, la pantalla `/Verify` que usan todos los operadores activos. Se dispara en la carga de página y cada 15 minutos (reset del caché).

6. **"Internal connection fatal error"** es un error de `Microsoft.Data.SqlClient` a nivel de protocolo/transporte, no de lógica SQL. Indica que la conexión TCP con SQL Server se interrumpió, frecuentemente por carga extrema o pool de conexiones agotado en el servidor.

7. El timestamp `11:54:49` del error coincide con el período de liveness failures confirmado por K8s.

## RELACIÓN CON LIVENESS

**Directa y mecánica.** La `lock(this)` en `ConnectionProvider.Create()` sobre un objeto Singleton hace que todos los threads concurrentes esperen bloqueados hasta 30 segundos cuando SQL Server está degradado. Con suficientes usuarios activos en `/Verify`, el Thread Pool de Kestrel se agota y no puede atender ninguna request, incluyendo `GET /health/liveness`. La probe de K8s agota su deadline → `context deadline exceeded` → reinicio del pod.

---

## CAMBIO MÍNIMO

**Reducir `Connect Timeout` de 30 a 5 segundos** en la connection string del `DIExtract`. Esto acota el bloqueo máximo por thread de 30 s a 5 s, reduciendo la duración de la starvation del Thread Pool proporcionalmente.

El cambio está en el valor configurado de `Connect Timeout` que llega a Program.cs (appsettings o EnvironmentDetector). No requiere modificar código.

## DESCONOCIDO

- **Por qué SQL Server (`LWVTDBSQLA007`/`DIExtract`) está generando "Internal connection fatal error"** — requiere revisar el error log del SQL Server, el pool de conexiones del servidor, y el número de conexiones abiertas simultáneas desde el pod.
- **Si otros DAL que usan `ConnectionProvider` con el mismo connection string** generan el mismo contention de `lock` bajo carga — el patrón es idéntico en todos los 44+ archivos DAL que usan `IDBConnectionHandler`, pero solo `IRegexValidationMemo` es Singleton.
- **Si el EnvironmentDetector** está devolviendo una connection string diferente al appsettings (con un `Connect Timeout` distinto).
- **Cuántos usuarios concurrentes** hay en `/Verify` en el momento del incidente.

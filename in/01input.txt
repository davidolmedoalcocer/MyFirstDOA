  1. Causa comprobada Fueron tres fallos encadenados:
  - No había servidor ado en ningún archivo MCP que carga el agente. kiro-cli mcp status --name ado respondía No MCP server named 'ado' found
  in any agent, y ~/.kiro/settings/mcp.json no existía.
  - La versión que configuraría el propio framework no arranca en este Dev Container. infios-sdlc fija ADO_VERSION = '2.10.0'

  llega por la dependencia @azure/msal-node-extensions; la 2.11.0 oficial ya no la incluye.
  - Aun con un servidor que funciona, había una carrera de arranque en Kiro v3. El primer mensaje salió a las 22:14:25 y el servidor conectó a
  las 22:14:31, así que el agente respondió ADO_TOOLS_UNAVAILABLE. Kiro solo espera a los servidores marcados con waitForReady.
  
  No era un problema de autenticación, de permisos ni de política corporativa. El perfil empresarial tiene MCP activado y sin lista de
  servidores permitidos.
  
  La advertencia de Workspace Trust es otro mecanismo y además un falso positivo. permissions.yaml dice workspaceTrusted: true, pero el
  framework busca un .trust-migration.json que Kiro ya no crea (kiro-engine.cjs:185). Hay 0 señales reales de carpeta no confiable en los
  registros.
  
  2. Configuración corregida Es el servidor local oficial de Microsoft. El servidor remoto mcp.dev.azure.com no sirve todavía para Kiro: según
  Microsoft, necesita un registro OAuth dinámico en Entra que aún no existe para este tipo de clientes.
  
  "ado": {
    "command": "npx",
    "args": ["-y","@azure-devops/mcp@2.11.0","highjumpvso","-d","core","work","work-items","-a","azcli"],
    "env": { "ado_mcp_project": "Development Tools" },
    "timeout": 120000,
    "waitForReady": true
  }

Informe técnico: caso 01, errores EACCES en node_modules de Infios Dev Portal
  
  1. Título del caso
  
  Caso 01: errores EACCES en node_modules del volumen compartido entre el Dev Container y los contenedores Admin UI y Tenant UI.
  
  2. Descripción del error original
  
  Según la evidencia que ustedes reportaron:
  
  - La tarea Dev: Start UI fallaba con EACCES en sharedUIComponents/node_modules/.bin y en adminUi/node_modules/@tsconfig/node22.
  - Esas rutas tenían archivos con propietario root:root.
  - El Dev Container trabaja como node, UID/GID 1000.
  - La tarea ejecuta pnpm install desde el Dev Container antes de levantar los contenedores
  (.workspaceScripts/task_startDevPortalDevUI.sh:15-22). Como node no puede modificar archivos de root, pnpm falla.
  - Se recuperó temporalmente con chown.
  
  3. Causa comprobada
  
  El conflicto de permisos está comprobado. Las dos partes escriben en el mismo volumen con UIDs distintos:
  - El Dev Container, como UID 1000.
  - Los contenedores dev-portal-admin-ui y dev-portal-tenant-ui. Antes del fix no declaraban user:, y node:24.22.1-alpine sin USER se ejecuta
  como root (adminUi/Dockerfile.dev, tenantUi/Dockerfile.dev, sin USER).
  
  Ambos montan devcontainer_workspace:/app (docker-compose-devui.yml). Es un volumen con nombre, así que la propiedad de los archivos se
  guarda como UID numérico. No hay traducción de usuarios entre el host y el contenedor, tampoco en Windows.
  
  El proceso histórico que creó esos archivos como root no está identificado.
  - Las rutas afectadas son artefactos de instalación: enlaces en .bin y el paquete @tsconfig/node22. Eso indica una instalación de
  dependencias ejecutada como root contra el volumen.
  - El código actual no contiene ese escritor:
    - Los contenedores de UI solo ejecutan pnpm dev (Dockerfile.dev:11).
    - No hay verify-deps-before-run, preinstall, postinstall ni predev en el repositorio.
    - Las instalaciones del flujo corren como node (task_startDevPortalDevUI.sh:17, task_setupSdlc.sh:236).
  
  - Con root, pnpm dev (Vite) solo crearía node_modules/.vite. Eso no explica .bin ni @tsconfig/node22.
  - Corrijo así la hipótesis de mi informe anterior: la caché de Vite no explica las rutas observadas.
  - El origen más probable es un pnpm install como root ejecutado fuera del flujo versionado actual (por ejemplo, un docker exec manual o una
  versión anterior). Es una inferencia sin evidencia.
  
  4. Solución implementada
  
  Revisé el diff contra HEAD (10ff3544). Estos son los cambios exactos:
  
  .devcontainer/detect-and-write-volume.sh:67-73
  
  # Use the Dev Container user's UID/GID for shared-volume writers
  DEV_UID="$(id -u)"
  DEV_GID="$(id -g)"
  
  printf 'DEV_UID=%s\nDEV_GID=%s\n' "$DEV_UID" "$DEV_GID" >> "$ENV_FILE"
  
  echo "Wrote DEV_UID=$DEV_UID DEV_GID=$DEV_GID to $ENV_FILE" >> "$LOG"
  
  docker-compose-devui.yml:15 y :30
  
      user: "${DEV_UID}:${DEV_GID}"
  
  Por qué funciona:
  - Mismo UID para todos los escritores. Los comandos postCreateCommand y postStartCommand se ejecutan como el usuario remoto (node). Por eso
  id -u e id -g devuelven exactamente el UID/GID con el que trabaja el Dev Container. Los contenedores de UI escriben con ese mismo UID y
  desaparece el escritor root de este flujo.
  - Sin duplicados en .env. .env se regenera en cada ejecución con cp .env.template (línea 57). El >> no acumula líneas porque .env.template
  no define DEV_UID ni DEV_GID (verificado).
  - Se ejecuta al crear y al arrancar. postCreateCommand.sh:5 y postStartCommand.sh:13 ya llamaban a este script en HEAD. No se modificaron ni
  hacía falta (git diff HEAD sobre ambos está vacío).
  - No hay que editar .env a mano. .env está ignorado (.gitignore:1: /.env) y se genera en cada arranque. Solo .env.template está versionado.
  - UID distinto de 1000. Si Dev Containers reasigna el UID de node en un host Linux o WSL (updateRemoteUserUID), id -u devuelve ese UID nuevo
  y Compose lo usa. El análisis estático es correcto. No se ha ejecutado (ver sección 6).
  
  Defectos y riesgos encontrados:
  - Sin valor por defecto en Compose. ${DEV_UID} no tiene valor de respaldo. Si .env no contiene la variable, Compose solo avisa y resuelve
  user: ":". Esto pasa en un Dev Container que se actualiza a esta rama sin reiniciar, o si se ejecuta Compose fuera del Dev Container. El
  inicio fallaría o tendría un comportamiento no definido. No es destructivo, y el siguiente arranque o una ejecución del script lo corrige.
  - El fix no repara volúmenes existentes. Los archivos que root ya creó siguen siendo de root. En su volumen, find -uid 0 devolvió cero, pero
  otros desarrolladores pueden necesitar el chown una vez.
  - UID sin entrada en /etc/passwd. En Alpine, un UID distinto de 1000 no tiene usuario en /etc/passwd, así que HOME=/. Vite escribe en
  node_modules y no debería afectar, pero no está validado.
  
  Cambios ajenos al caso 01 en el árbol de trabajo:
  - Modificados: .gitignore, .kiro/settings/cli.json, .kiro/steering/uikit-usage.md.
  - Sin seguimiento: .kiro/hooks/, .kiro/settings/mcp.json, .kiro/steering/uikit-foundations.md.
  
  Son configuración del framework SDLC y no deben entrar en el commit del caso 01. El caso solo comprende
  .devcontainer/detect-and-write-volume.sh y docker-compose-devui.yml.

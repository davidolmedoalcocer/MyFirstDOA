01

File permissions when starting Dev Portal

Fix implemented
↑ Contents

Prevented the UI containers from creating files owned by a different user than the developer environment.

What was happening

When running “Dev: Start UI” in VS Code, dependency installation could fail with “EACCES: permission denied”. Some node_modules directories belonged to the Linux administrator (root), while the installation ran as the regular node user.

Why it happened

Admin UI and Tenant UI did not specify a runtime user in Docker Compose. Their images therefore ran as root by default. If such a process wrote to shared directories, the node user could subsequently lack permission to modify the files. The exact historical process that originally created the root-owned files was not identified.

What changed

Configured both UI services to use the same user and group IDs as the Dev Container. A second script detects those IDs and stores them in .env, avoiding an assumption that every developer account uses UID 1000.

Files and code: BEFORE / AFTER

docker-compose-devui.ymlLines 15 and 30, according to the previous investigation · Runtime identity for the two UI services.
BEFORE
# Neither Admin UI nor Tenant UI specified a "user:" property.
# Docker used the image’s default user: root.
AFTER
user: "${DEV_UID:-1000}:${DEV_GID:-1000}"
Why it matters: The user property tells Docker which identity to use when starting each container. DEV_UID and DEV_GID contain the developer’s numeric user and group IDs. The :-1000 syntax supplies 1000 if a variable is unset or empty. This overrides the images’ default root identity for these services.
.devcontainer/detect-and-write-volume.shApproximately lines 67–73, according to the previous investigation · Detects the developer identity during Dev Container setup.
BEFORE
# The script did not yet write DEV_UID or DEV_GID to .env.
AFTER
DEV_UID="$(id -u)"
DEV_GID="$(id -g)"
printf 'DEV_UID=%s\nDEV_GID=%s\n' "$DEV_UID" "$DEV_GID" >> "$ENV_FILE"
Why it matters: id -u returns the numeric user ID, and id -g returns the numeric group ID. printf writes both values to .env, which Docker Compose reads when starting the UIs. This is not the same as chown: chown changes the owner of existing files, while user changes the identity of new processes.

Verification and outcome

The BEFORE demonstration reproduced the permission failure; the AFTER demonstration completed the installation and both interfaces responded. The fix prevents new ownership mismatches but does not automatically change ownership of existing files.

02

Opening the applications at the correct browser addresses

Fix implemented
↑ Contents

Adjusted automatic browser launching so each application opens at its intended URL and port.

What was happening

When starting the UIs from VS Code, the browser could open a forwarded port instead of the correct port on Windows. The address sometimes had to be corrected manually.

Why it happened

VS Code attempted to create a tunnel to ports inside the Dev Container, even though Docker exposed the applications through Windows. An initial workaround that changed the hostname avoided the tunnel but triggered a CORS restriction when the page called the API.

What changed

Supplied the full URL path for each UI and changed the browser-launch mechanism. The helper sends LOCALHOST internally to VS Code; Chrome ultimately uses localhost, preserving the origin expected by the API.

Files and code: BEFORE / AFTER

.workspaceScripts/task_startDevPortalDevUI.shLines 28 and 30 · URLs passed from the development task to the browser.
BEFORE
28  bash ./.workspaceScripts/open-when-ready.sh http://localhost:35001/ 120 \
30  bash ./.workspaceScripts/open-when-ready.sh http://localhost:35002/ 120 \
AFTER
28  bash ./.workspaceScripts/open-when-ready.sh http://localhost:35001/devportal/adminui/ 120 \
30  bash ./.workspaceScripts/open-when-ready.sh http://localhost:35002/devportal/tenantui/ 120 \
Why it matters: Previously, the helper was asked to open only each port’s root address. It now opens the specific Admin UI or Tenant UI page. This makes the target address precise, but does not by itself prevent incorrect tunnel creation.
.workspaceScripts/open-when-ready.shLine 26; lines 28–35 and 42 · Mechanism used to tell VS Code which URL to open.
BEFORE
# Previous browser launch (documented excerpt):
timeout 10 "$BROWSER" "$BROWSER_URL" >/dev/null 2>&1 || true
AFTER
26  OPEN_URL=$(printf '%s' "$BROWSER_URL" | sed -E 's#^(https?://)localhost(:[0-9]+)#\1LOCALHOST\2#')
28  open_in_browser() {
29    if [ -n "$VSCODE_IPC_HOOK_CLI" ] && command -v curl >/dev/null 2>&1; then
30      timeout 10 curl -fsS --unix-socket "$VSCODE_IPC_HOOK_CLI" -H 'content-type: application/json' \
31        -d "{\"type\":\"openExternal\",\"uris\":[\"$OPEN_URL\"]}" http://localhost/ >/dev/null 2>&1 && return
32    fi
33    # If the socket call fails, use the original browser helper.
34    [ -n "$BROWSER" ] && timeout 10 "$BROWSER" "$BROWSER_URL" >/dev/null 2>&1
35  }
42  open_in_browser || true
Why it matters: Line 26 temporarily changes localhost to LOCALHOST in the internal request. Lines 28–31 send this URL to VS Code without letting the former browser launcher normalize it first. Chrome treats the hostname as localhost, so the page keeps the origin expected by the API. Line 34 provides a fallback; line 42 calls the helper once the page is ready.

Verification and outcome

The “Dev: Start UI” task was run again and both applications opened correctly. Neither Docker port mappings nor the API’s CORS security rules were changed. The VS Code internal mechanism may need review if VS Code changes in the future.

03

Connecting Kiro to Azure DevOps

Integration configured
↑ Contents

Enabled Kiro to query Azure DevOps through a personal integration without modifying shared repository settings.

What was happening

Kiro did not have the Azure DevOps (ADO) tool available, and an SDLC configuration check displayed warnings. The previously suggested connector version failed to start in this environment.

Why it happened

No MCP server named ado was available to the agent. Version 2.10.0 could not start because a system dependency was missing; another attempt used the connector before it was ready.

What changed

Configured the official Azure DevOps MCP connector version 2.11.0 in Kiro’s personal settings, reusing the existing Azure CLI authentication and instructing Kiro to wait until the MCP server is ready.

Files and code: BEFORE / AFTER

~/.kiro/settings/mcp.jsonJSON configuration keys; exact line numbers in the personal file were not established · Connector configuration for Kiro to query Azure DevOps.
BEFORE
// No personal MCP server named "ado" was configured.
// The existing configuration did not provide this integration to Kiro.
AFTER
"mcpServers": {
  "ado": {
    "command": "npx",
    "args": ["-y", "@azure-devops/mcp@2.11.0", "…", "-a", "azcli"],
    "timeout": 120000,
    "waitForReady": true
  }
}
Why it matters: ado is the connector name; npx starts the program; 2.11.0 identifies the version; azcli reuses the existing Azure CLI sign-in; waitForReady tells Kiro not to use the connector until it is available. The ellipsis represents omitted organization-specific arguments. This is an excerpt, not a complete JSON configuration to copy.
.kiro/agents/sdlc.jsonincludeMcpJson property (unchanged) · Existing SDLC agent setting.
BEFORE
"includeMcpJson": true
AFTER
"includeMcpJson": true  // Unchanged
Why it matters: The agent was already configured to load MCP connections. No edit was needed here; the working change was adding the connector to the personal settings.

Verification and outcome

Kiro performed a read-only query and returned a list of 38 projects, according to the recorded demonstration. No tracked project files were modified. An older SDLC-check warning may still appear because that checker examines a different configuration.

Correcting UIKit documentation paths

Fix implemented
↑ Contents

Updated internal paths so Kiro can find the component manuals installed in the project.

What was happening

Kiro’s steering instructions pointed to a UIKit manual directory that did not exist at the repository root. The manuals were actually installed under sharedUIComponents.

Why it happened

The setup script copied the steering documents without adapting their paths to Dev Portal’s directory structure. Running setup again would therefore restore the incorrect paths.

What changed

Changed the setup script to rewrite the relevant paths while copying the steering files. Then regenerated Kiro’s steering document with the correct locations.

Files and code: BEFORE / AFTER

.workspaceScripts/task_setupSdlc.shLines 243–255 (changed area) · Generates the instruction files read by Kiro.
BEFORE
243  UIKIT_STEERING="sharedUIComponents/node_modules/@infios/uikit/dist/steering"
245  if [ -d "$UIKIT_STEERING" ]; then
246      cp "$UIKIT_STEERING"/*.md "$KIRO_DIR/steering/"
247      info "Copied UIKit steering files from $UIKIT_STEERING"
AFTER
243  UIKIT_STEERING="sharedUIComponents/node_modules/@infios/uikit/dist/steering"
245  if [ -d "$UIKIT_STEERING" ]; then
250      for file in "$UIKIT_STEERING"/*.md; do
251          sed -E \
252              -e 's#(^|[^/A-Za-z0-9_.-])node_modules/@infios/uikit\.test/#\1e2e/node_modules/@infios/uikit.test/#g' \
253              -e 's#(^|[^/A-Za-z0-9_.-])node_modules/@infios/uikit/#\1sharedUIComponents/node_modules/@infios/uikit/#g' \
254              "$file" > "$KIRO_DIR/steering/$(basename "$file")"
255      done
Why it matters: Previously, cp copied each text file without editing its contents, even when its paths were wrong. The new for loop processes each steering document; sed replaces UIKit paths with the correct sharedUIComponents prefix and testing paths with e2e. The result is written into Kiro’s steering directory so the next setup does not reintroduce the error.
.kiro/steering/uikit-usage.mdLines 9, 121, 152, and 313 · Steering document telling Kiro where to look for UIKit documentation.
BEFORE
L9    node_modules/@infios/uikit/dist/steering/components/
L121  node_modules/@infios/uikit/dist/steering/uikit-foundations.md
L313  node_modules/@infios/uikit.test/dist/steering/uikit-testing-patterns.md
AFTER
L9    sharedUIComponents/node_modules/@infios/uikit/dist/steering/components/
L121  sharedUIComponents/node_modules/@infios/uikit/dist/steering/uikit-foundations.md
L313  e2e/node_modules/@infios/uikit.test/dist/steering/uikit-testing-patterns.md
Why it matters: The corrected links now point to the locations used by Dev Portal. In particular, the normal UIKit package lives under sharedUIComponents/node_modules rather than at the repository root. References to the test package point to e2e/node_modules; the package was not installed, so physical access to those two test manuals was not verified.

Verification and outcome

Kiro successfully read an installed UIKit button manual, and four documented references were corrected. The UIKit.test references were adjusted structurally but their actual files could not be checked because that package was not installed.

05

Preserving Dozzle settings between restarts

Fix implemented
↑ Contents

Prevented Dozzle preferences from being lost when its container is removed and recreated.

What was happening

Dozzle, the tool used to view application logs, saved settings inside its own container. The task that stops Dozzle also removes that container, so its configuration could disappear.

Why it happened

Dozzle’s /data directory was not backed by a persistent volume. The “orphan containers” warning was expected because several Docker Compose files share the same project, so it did not require a code fix.

What changed

Added a named Docker volume, dozzle_data, mounted at /data. Settings now live outside the disposable container and remain available when it is recreated.

Files and code: BEFORE / AFTER

docker-compose-dozzle.ymlBEFORE lines 8–9; AFTER line 14 and lines 18–19 · Directories and storage mounted by Dozzle.
BEFORE
8   volumes:
9     - "/var/run/docker.sock:/var/run/docker.sock"

# No persistent volume was mounted at /data.
AFTER
8   volumes:
9     - "/var/run/docker.sock:/var/run/docker.sock"
14    - "dozzle_data:/data"

18  volumes:
19    dozzle_data:
Why it matters: The Docker socket on line 9 only lets Dozzle communicate with Docker; it does not save preferences. Line 14 mounts persistent storage named dozzle_data at /data in the container. Lines 18–19 declare this volume. When the task removes the container, the volume remains because the down command does not include -v.
.workspaceScripts/task_dozzle.shLines 6–7 (reviewed, unchanged) · Starts Dozzle, then removes its container when the task finishes.
BEFORE
6  docker compose -f ./docker-compose-dozzle.yml up --abort-on-container-exit
7  docker compose -f ./docker-compose-dozzle.yml down >/dev/null 2>&1
AFTER
# Unchanged: this task was not modified.
Why it matters: Line 7 removes the container, but not the named volume. The persistent-data fix therefore belonged in docker-compose-dozzle.yml, not in this script. No destructive Docker commands need to be run to explain the change.

Verification and outcome

Functional tests performed before the testing incident showed lost settings in the BEFORE scenario and retained settings in the AFTER scenario. Later final demonstrations inspect configuration files only; they do not rerun Docker. The test incident and subsequent environment recovery are documented.

06

Understanding exit code 137 when stopping Dozzle

Analysis closed · no changes
↑ Contents

Established what exit code 137 means and why no repository change was required.

What was happening

When Dozzle was stopped from the terminal, “exited with code 137” appeared. It was unclear whether that message indicated a defect in the application.

Why it happened

Exit code 137 indicates that a container was terminated by SIGKILL. This can happen if Ctrl+C is pressed a second time or the graceful-stop timeout expires. The original event log was not available, so the exact historical trigger cannot be established.

What changed

No repository files were changed. Docker Compose shutdown behavior was explained: press Ctrl+C once and allow the container to stop normally.

Files and code: BEFORE / AFTER

.workspaceScripts/task_dozzle.shLines 6–7 (unchanged) · Explains where the message originates and what happens when Dozzle stops.
BEFORE
6  docker compose -f ./docker-compose-dozzle.yml up --abort-on-container-exit
7  docker compose -f ./docker-compose-dozzle.yml down >/dev/null 2>&1
AFTER
# Code unchanged.
# Recommended: press Ctrl+C once and allow shutdown to complete.
Why it matters: Line 6 starts Dozzle and streams its logs. On shutdown, Docker normally requests a graceful stop. A second Ctrl+C can force SIGKILL and produce code 137 (128 + signal 9). Once the first command ends, line 7 removes the container, while the persistent volume created in the preceding improvement remains.
.vscode/tasks.jsonLines 80–86 (unchanged) · Defines the “Logs: Dozzle” task in VS Code.
BEFORE
"label": "Logs: Dozzle"
// The task description indicates that Ctrl+C stops the task.
AFTER
# Unchanged: the behavior was already expected.
Why it matters: The task simply launches task_dozzle.sh. Investigation found no defect justifying a change. The demonstrations use simulated Docker; they do not establish the exact cause of the historical exit code 137.

Verification and outcome

The mechanisms were reproduced using simulated Docker, without affecting real containers. The issue is closed as an explanation of expected behavior, not as a software fix.

07

Setting the correct Kiro sign-in region

Fix implemented
↑ Contents

Changed the default region to us-east-2, as requested by Eli.

What was happening

The “Setup SDLC Framework” task constructed Kiro’s sign-in command using us-east-1, although Eli specified that the correct region is us-east-2.

Why it happened

The wrong region was hard-coded in a setup-script variable. That variable was then inserted into the sign-in command.

What changed

Changed a single line from us-east-1 to us-east-2. No other regions, credentials, or command arguments were changed.

Files and code: BEFORE / AFTER

.workspaceScripts/task_setupSdlc.shLine 18 (changed); lines 129, 133, and 139 (usage unchanged) · Selects the AWS region passed to the Kiro sign-in command.
BEFORE
18  KIRO_REGION="us-east-1"
AFTER
18  KIRO_REGION="us-east-2"
129 KIRO_LOGIN="kiro-cli login --license pro --identity-provider $KIRO_IDENTITY_PROVIDER --region $KIRO_REGION --use-device-flow"
133 $KIRO_LOGIN || true
Why it matters: Line 18 defines the region Kiro should use for sign-in. Line 129 builds the command using that variable, and line 133 executes it when needed. With the new value, the command receives --region us-east-2. Line 139 displays that same value if sign-in needs to be retried.

Verification and outcome

The authentication block was tested with a simulated Kiro CLI. The command received --region us-east-2, and the printed retry command used the same value. No live authentication was performed.

Linking to the official Dev Portal documentation

Documentation updated
↑ Contents

Added a section to the main README explaining what official documentation exists and when to use it.

What was happening

The project’s main README explained setup and how to run the application, but did not direct readers to the official documentation covering how to use Dev Portal.

Why it happened

The main entry point for a new developer was missing a clear reference to that user-facing guide.

What changed

Added a Documentation section with the official link, what the Admin Portal guide covers, the stated status of the Customer Portal guide, and when to consult those materials.

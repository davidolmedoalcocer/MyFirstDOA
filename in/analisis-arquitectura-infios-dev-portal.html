1. Resumen ejecutivo

HECHO Verificado leyendo directamente código/configuración del repositorio.
INFERENCIA Conclusión razonada a partir de evidencia indirecta o convención.
DESCONOCIDO No se puede determinar desde este repositorio.

HECHO Dev Portal es una solución multi-proyecto para la gestión de tenants y despliegue de servicios dentro de Infios Platform (README.md). Se compone de:

  • Un backend .NET (devPortalService/) con API REST + OData sobre PostgreSQL.
  • Dos SPAs en Vue 3 (adminUi/ para administradores, tenantUi/ para clientes/tenants) que comparten lógica vía un paquete interno (sharedUIComponents/).
  • Una base de datos PostgreSQL gestionada con Liquibase (database/).
  • Un entorno de desarrollo basado en Dev Container + Docker Compose.
  • Manifiestos de Kubernetes (k8s/) para despliegue en el clúster de "Platform", usando Kong como gateway/API Manager.
  • Pruebas end-to-end con Playwright (e2e/).
Dependencia crítica externa: el sistema depende de un repositorio/entorno "Platform" (PlatformV2) externo a este repo para autenticación, autorización, multi-tenencia y otros servicios compartidos (sesión, seguridad, Kong). Esta es la pieza menos autocontenida de la arquitectura — ver sección Platform API y Seeder.

4.2 Cómo se inicia y configura HECHO

Punto de entrada: devPortalService/src/Program.cs. En el arranque:

  1. Lee ConnectionStrings:DefaultConnection y configura DevPortalDbContext con UseNpgsql.
  2. Escanea ensamblados en busca de clases marcadas con [RegisterToDI] y las registra automáticamente (Api/Extensions/Setup/ServiceRegistrationExtensions.cs).
  3. Configura OData, FluentValidation, Swagger, CORS (según Cors:AllowedOrigins en appsettings.Development.json) y health checks (/livez, /readyz).
  4. Divide el pipeline HTTP en dos ramas (app.Map("/admin", ...) y app.Map("/customer", ...)), marcando el segmento de ruta en HttpContext.Items. El mismo backend sirve tanto a Admin UI como a Tenant UI, diferenciando por prefijo de ruta.
  5. Para peticiones que llegan directo desde Kong (sin prefijo en el path), lee un header personalizado para inferir si es admin o customer.

Configuración de desarrollo (devPortalService/src/appsettings.Development.json):

"DefaultConnection": "Host=dev-portal-postgres;Port=5432;Database=devPortal;Username=devPortal;Password=devPortal!"

(Credencial de desarrollo local, no sensible — está versionada en el repo tal cual.)

En docker-compose.yml, el backend corre con la imagen mcr.microsoft.com/dotnet/sdk:10.0, montando el workspace completo y ejecutando dotnet watch run (hot reload) dentro del contenedor — no se compila una imagen propia en dev, a diferencia de producción (docker-compose-prodservice.yml, imagen ghcr.io/infios-tools/devportal-service).

4.3 Controladores y servicios HECHO

  • Controladores REST "planos": UsersController (/api/users/current), TenantDeploymentController, SettingReferenceController, ProductRegistrationController.
  • Controladores OData en Api/Controllers/OData/*: TenantsController, CustomersController, ProductsController, ProductVersionsController, DeploymentRequestsController, SettingsController, TemplatesController, etc. — exponen CRUD + consultas OData ($filter, $expand) sobre cada entidad de dominio.
  • Patrón base reutilizable en Api/Controllers/OData/BaseOdataControllers/ (Get, GetById, Post, Put, Patch, Delete genéricos) que los controladores concretos heredan/extienden.
  • La lógica de negocio real vive en Domain.Services/*.cs, inyectada vía interfaces de Domain/Services/Interfaces/.

4.4 Acceso a base de datos HECHO

  • ORM: Entity Framework Core con proveedor Npgsql (Npgsql.EntityFrameworkCore.PostgreSQL, ver DevPortalService.csproj).
  • Infrastructure/DevPortalDbContext.cs expone DbSet<T> para cada entidad (Tenants, Products, ProductVersions, Customers, DeploymentRequests, Settings, SettingVersions, Users, etc.) y aplica configuraciones de mapeo vía modelBuilder.ApplyConfigurationsFromAssembly, definidas en Infrastructure/Configurations/*.cs (patrón IEntityTypeConfiguration<T>, un archivo por entidad).
  • Los repositorios (Infrastructure/Repositories/*.cs) encapsulan las consultas EF Core detrás de interfaces de dominio (Domain/Repositories/Interfaces/*.cs), siguiendo el patrón Repository.
  • Health check de disponibilidad de BD vía AddHealthChecks().AddDbContextCheck<DevPortalDbContext>(), expuesto en /readyz.

4.5 Base de datos — motor, alojamiento y migraciones HECHO

  • Motor: PostgreSQL 16 (image: postgres:16, docker-compose.yml).
  • En desarrollo corre como contenedor Docker dev-portal-postgres-db, con credenciales devPortal / devPortal! y base de datos devPortal (mismas credenciales de entorno local/CI en docker-compose.yml, docker-compose-testing.yml, docker-compose-prodservice.yml — no son credenciales de producción real).
  • Persistencia física: volumen Docker nombrado pg_data montado en /var/lib/postgresql/data (docker-compose.yml, sección volumes:). Es un volumen gestionado por Docker (no un bind-mount a una ruta visible del host); los datos sobreviven a docker compose down pero solo se eliminan con docker compose down -v o docker volume rm.
  • Migraciones de esquema: el esquema productivo se gestiona por Liquibase, no por dotnet ef database update directamente contra el entorno compartido (aunque el readme del servicio documenta el flujo clásico de EF Core para desarrollo local de migraciones individuales).

4.6 Cómo funciona Liquibase HECHO

  • Imagen construida en database/Dockerfile: parte de Ubuntu 22.04, instala un JRE fijado por motivos de seguridad (mitigación de CVE) y copia los binarios de liquibase/liquibase:4.31.1.
  • Changelog maestro: database/liquibase/master.yaml, que incluye en orden estricto (documentado con comentarios sobre dependencias de claves foráneas) los archivos de database/liquibase/tables/*.yaml:
users → cluster_groups → clusters → customers → customer_public_tenants → tenants → products → product_versions → tenant_product_versions → settings → setting_versions → product_version_settings → tenant_settings → deployment_requests → deployment_request_product_versions → deployment_request_settings → templates → template_product_versions → template_settings → drop_legacy_config_secret_tables
  • También incluye tables_e2e/test_seed_data.yaml, activado solo bajo el contexto testing (LIQUIBASE_CONTEXTS=testing en docker-compose-testing.yml).
  • El ENTRYPOINT del contenedor espera a que Postgres esté listo (pg_isready) y luego ejecuta liquibase update contra jdbc:postgresql://${DB_HOST}:${DB_PORT}/${DB_NAME}.
  • En docker-compose.yml, el servicio dev-portal-liquibase se construye localmente (build: ./database) y depende de dev-portal-postgres; el backend depende a su vez de que Liquibase termine. En docker-compose-testing.yml esto es explícito con condition: service_completed_successfully; en docker-compose.yml el depends_on solo ordena arranque de contenedor, sin esperar healthcheck.

5. Frontend

5.1 Construcción HECHO

  • adminUi y tenantUi son dos aplicaciones Vue 3 independientes, cada una con su propio package.json, vite.config.ts, Dockerfile (prod) y Dockerfile.dev (desarrollo con hot-reload vía nginx + entrypoint).
  • Gestor de paquetes: pnpm (lockfiles pnpm-lock.yaml en adminUi/, tenantUi/, sharedUIComponents/, e2e/; .npmrc apunta a un registro con paquetes privados, ej. @infios/uikit).
  • Bundler: Vite. adminUi/vite.config.ts fija base: '/devportal/adminui' en modo serve y alias @devportal/shared-ui apuntando directamente al código fuente de sharedUIComponents/src (no al paquete compilado) — en desarrollo el componente compartido se consume como fuente viva, sin build intermedio.
  • UI Kit: usan el design system @infios/uikit (steering obligatorio según .kiro/steering/uikit-usage.md), con componentes <infios-*> registrados como custom elements.

5.2 Componentes compartidos HECHO

sharedUIComponents/ es un paquete interno (no una app desplegable) con:

  • src/auth/auth.ts — lógica de autenticación común (login, refresco de sesión, callback).
  • src/api/httpClient.ts, apiClient.ts, odataUtils.ts — cliente HTTP genérico basado en fetch.
  • src/stores/user.ts — store Pinia que llama a GET {backendUrl}/api/users/current para resolver la identidad.
  • src/components/, src/views/, src/layouts/, src/composables/, src/dto/, src/models/, src/services/ — UI y lógica de negocio de frontend reutilizada por ambas apps.

Ambas UIs importan estos módulos vía el alias @devportal/shared-ui (ver adminUi/vite.config.ts, adminUi/src/router/index.ts).

5.3 Comunicación con el backend HECHO

  • El frontend llama al backend mediante fetch con rutas relativas (ej. ${utils.getBackendUrl()}/api/users/current en sharedUIComponents/src/stores/user.ts).
  • En desarrollo con Docker (docker-compose-devui.yml), cada UI corre en su propio contenedor nginx; no hay evidencia de proxy directo configurado ahí hacia el backend.
  • En testing (docker-compose-testing.yml, tenantUi/nginx.testing.conf), nginx actúa de reverse proxy: location /devportal/service/ { proxy_pass http://dev-portal-service-testing:8080/customer/; }.
  • En producción/Kubernetes, Kong es el gateway: las rutas /devportal/service/admin y /devportal/service/customer (k8s/dev-portal-service-admin-kong-ingress.yaml y su equivalente de customer) se enrutan al servicio dev-portal-service, que internamente usa el prefijo de ruta para decidir el pipeline.
  • Variable BACKEND_SERVICE_URL (ver docker-compose-produi.yml, tenantUi/entrypoint.sh) se inyecta en tiempo de arranque del contenedor nginx vía envsubst sobre index.html.template, permitiendo configurar el backend sin rebuild de imagen.

6.3 Kubernetes HECHO

k8s/ contiene manifiestos para integrar Dev Portal en el clúster compartido de "Platform" (namespace platform), no un despliegue Kubernetes autocontenido:

  • dev-portal-services.yaml / dev-portal-services-template.yaml: Service + EndpointSlice que apuntan, vía IP fija (192.168.65.254, típica de Docker Desktop/minikube), a los contenedores Docker locales — es decir, puente entre el entorno Docker Compose local y el clúster Kubernetes de Platform usado en desarrollo.
  • dev-portal-*-kong-ingress.yaml: Ingress de Kong con plugins (strip-path, autorización, segmentación de ruta) que exponen el backend bajo /devportal/service/admin y /devportal/service/customer.
  • dev-portal-auth-plugin-*.yaml: KongClusterPlugin de tipo kong-plugin-authorization que valida sesiones contra servicios de Platform (k1-services-security, k1-services-session).
  • dev-portal-ui-ingress-dev.yaml / -prod.yaml: ingress para las SPAs.
En resumen: Kubernetes cumple aquí el rol de gateway/autenticación/enrutamiento compartido de la plataforma, no de orquestador de los propios contenedores de Dev Portal en desarrollo (esos corren en Docker Compose).

7. Autenticación

7.1 Mecanismo HECHO

La autenticación no es un login propio de Dev Portal ni usa OAuth de GitHub para usuarios finales. Es delegada por completo a "Platform":

  1. El frontend (sharedUIComponents/src/auth/auth.ts) redirige a {origin}/mobile-bff/v1/auth/signin?applicationId=...&connectionType=Mobile&callbackURL=... cuando detecta que no hay sesión (requireAuth() → redirectToLogin()).
  2. applicationId es distinto por UI: "Infios Admin Portal" en adminUi/src/auth/authInstance.ts (customer portal usaría otro valor análogo — DESCONOCIDO su literal exacto, no confirmado en esta pasada).
  3. Tras el login en Platform, este redirige a /auth/callback con un sessionToken; el frontend llama a POST /mobile-bff/v1/auth/acquire-session para intercambiar el token por una cookie de sesión (credentials: 'include').
  4. La sesión se refresca periódicamente con POST /mobile-bff/v1/auth/refresh-session cada 30s (intervalo configurable, refreshIntervalMs).
  5. Una vez autenticado, cada petición al backend llega (vía Kong) con headers inyectados por Platform: X-UserSessionModel (JSON con UserId, UserName, Tenant, etc. — Core/Models/UserSessionModel.cs), X-PrivateTenant, X-PublicTenant (Core/MultiTenancy/TenantHeaders.cs).
  6. El backend resuelve al actor de la petición en Api/Services/RequestActorResolver.cs: parsea X-UserSessionModel, hace upsert del usuario local, y determina si es "admin" según el segmento de ruta (admin vs customer) por el que entró la petición — no por un rol almacenado en la tabla users.

7.2 Integración con GitHub HECHO

No se encontró ningún mecanismo de login/OAuth contra GitHub para usuarios finales de Dev Portal. Las únicas referencias a "GitHub" en el código son:

  • Campo de dominio de negocio: CustomerDto.gitHubOrganization (sharedUIComponents/src/stores/user.ts, usado en CustomerDrawer.vue/CustomerInformation.vue) — probablemente para vincular la organización de GitHub del cliente a efectos de despliegue/CI, no de autenticación de usuarios.
  • Infraestructura de CI/CD: GitHub Actions (.github/workflows/ci.yml, cd.yml, release-promotion.yml) y GitHub Container Registry (ghcr.io/...) para build/scan/publicación de imágenes.
  • Autenticación de desarrollador con GitHub Packages (no de usuario final): .workspaceScripts/task_setupSdlc.sh usa gh auth login para obtener un token y configurar .npmrc contra npm.pkg.github.com (paquetes privados como @infios/uikit).
DESCONOCIDO Si el proyecto tiene en algún otro lugar (ej. configuración de Platform, fuera de este repo) un proveedor OAuth de GitHub para login de usuarios finales, no es visible desde este repositorio.

7.3 Dónde se configuran los permisos HECHO

  • Autorización de acceso al portal (quién puede entrar a admin vs. customer): plugins Kong kong-plugin-authorization-admin-portal / -customer-portal (k8s/dev-portal-auth-plugin-admin-portal.yaml, -customer-portal.yaml), que consultan servicios externos de Platform (securityService, sessionService) con un applicationId específico por portal.
  • Autorización a nivel de endpoint dentro del backend: Api/Filters/RoutePrefixFilter.cs — filtro de recurso ASP.NET Core que rechaza (404) peticiones que llegan por un segmento de ruta no permitido para ese controlador/acción, usando el atributo [ODataRoutePrefix(...)]. Regla fija: "admin" siempre está permitido en cualquier endpoint; "customer" requiere autorización explícita por atributo.
  • No existe una tabla de roles/permisos en el esquema de Liquibase (database/liquibase/tables/) — el modelo de permisos vive fuera del repo, en Platform.

8. Platform API y Seeder

8.1 Qué hace cada componente HECHO

  • dev-portal-seeder: contenedor efímero (restart: "no") que ejecuta una imagen externa, ghcr.io/infios-tools/dev-portal-seeder:${SEEDER_IMAGE_TAG} (docker-compose.yml, docker-compose-prodservice.yml). No tiene código fuente en este repositorio. Su función, según los comentarios del propio docker-compose.yml, es configurar datos iniciales en Platform para que Dev Portal funcione: crea un "Identity Claim" para el tenant, y puede configurar aspectos de Customer Portal / Admin Portal.
  • Platform API: servicio HTTP del "Platform" externo (API pública de la plataforma, ej. k1-api en el entorno real de Platform). El seeder necesita hablar con ella para crear el Identity Claim.

8.2 Por qué el puerto 35003 HECHO

En docker-compose.yml:

PLATFORM_API_URL: http://host.docker.internal:35003

Comentario textual en el mismo archivo:

"This value sets the URL that points to Platform's public API service. DEFAULT VALUE: http://k1-api:80"

El valor por defecto de la imagen del seeder (k1-api:80) asume que corre dentro de la red de Platform. Como en este repo el seeder corre en la red de Docker Compose de Dev Portal, se sobreescribe para apuntar, vía host.docker.internal, a un Platform API expuesto en el puerto 35003 del host — se asume que el entorno de "Platform" (levantado aparte, posiblemente desde el repo hermano PlatformV2) publica su API pública en ese puerto del host/devcontainer.

8.3 ¿Forma parte de este repositorio? HECHO

No. Ni el Seeder ni Platform API tienen código fuente en /workspaces/dev-portal. Evidencia:

  • Búsqueda de PlatformV2 en todo el árbol: 0 resultados (glob **/PlatformV2*).
  • El seeder se consume únicamente como imagen Docker publicada (image: ghcr.io/infios-tools/dev-portal-seeder:...), nunca como build: local.
  • task_startPlatform.sh hace cd PlatformV2 && docker compose ..., lo cual solo funcionaría si existiera un directorio PlatformV2 al mismo nivel que dev-portal (repo hermano clonado aparte, no una subcarpeta de este repo).

8.4 ¿Existe forma documentada de iniciarlo localmente? DESCONOCIDO

Dentro de este repositorio solo existe la referencia indirecta de .workspaceScripts/task_startPlatform.sh y task_stopPlatform.sh, que asumen un checkout externo de PlatformV2 con sus propios docker-compose y perfiles (interface, webhook, storage). No hay documentación dentro de /workspaces/dev-portal sobre cómo obtener o configurar ese repositorio (ni URL, ni instrucciones de clonado, ni variables de entorno necesarias para que sus servicios expongan el puerto 35003). Probablemente está documentado en el repositorio PlatformV2 mismo o en documentación de equipo fuera del código.

8.5 Qué funcionalidades quedan afectadas si no está disponible INFERENCIA razonada

  • El contenedor dev-portal-seeder fallará o no podrá completar su inicialización (no crea el Identity Claim ni configura Customer/Admin Portal) — pero como tiene restart: "no", no bloquea indefinidamente el resto del stack, aunque los datos de Platform quedarían sin sembrar.
  • La autenticación real end-to-end (login vía /mobile-bff/v1/auth/signin, resolución de sesión vía Kong) depende de que exista un Platform operativo (no solo su API pública en 35003, sino los servicios security/session referenciados en los plugins Kong). Sin Platform corriendo, el flujo de login quedará bloqueado en el estado redirecting (auth.ts).
  • El backend de Dev Portal sí puede arrancar y responder a /livez//readyz sin Platform, porque su única dependencia dura es PostgreSQL. Pero cualquier endpoint que dependa de X-UserSessionModel/X-PublicTenant (ej. UsersController.Current) devolverá 400 si esos headers no llegan — son los que inyecta Platform/Kong.
  • En modo DOTNET_ENVIRONMENT=Testing, el propio backend inyecta headers de prueba por defecto (Program.cs), lo que permite que los tests E2E (docker-compose-testing.yml) funcionen sin depender de Platform en absoluto.

9. Flujo de funcionamiento paso a paso

HECHO / INFERENCIA combinados, según el código revisado.

  1. El usuario abre el navegador en la URL de la UI (ej. adminUi, servida tras /devportal/adminui en dev local, o tras el ingress de Kong en el entorno real).
  2. El router de Vue (adminUi/src/router/index.ts) ejecuta router.beforeEach: si auth.isAuthenticated() es falso, llama a auth.requireAuth().
  3. requireAuth() redirige el navegador a {origin}/mobile-bff/v1/auth/signin?applicationId=...&callbackURL=... — ruta resuelta por Platform, no por Dev Portal.
  4. Tras autenticarse en Platform, el usuario regresa a /auth/callback con un sessionToken. El componente AuthCallback invoca auth.handleCallback(sessionToken).
  5. handleCallback llama a POST /mobile-bff/v1/auth/acquire-session con credentials: 'include': Platform fija una cookie de sesión en el navegador. El estado interno pasa a authenticated y arranca el bucle de refresco cada 30s.
  6. Se ejecuta userStore.initialize(), que hace fetch(GET {backendUrl}/api/users/current).
  7. En producción, la petición viaja a través de Kong: el Ingress aplica plugins (kong-publicapi-auth-platform, kong-tenant-plugin-platform, kong-plugin-authorization-admin-portal, kong-plugin-route-segment-admin-portal), que validan la cookie, resuelven el tenant, e inyectan los headers X-UserSessionModel, X-PrivateTenant, X-PublicTenant y el segmento de ruta antes de reenviar al servicio dev-portal-service (strip-path activado).
  8. El backend recibe la petición, guarda el segmento de ruta en HttpContext.Items, y ejecuta el pipeline: GlobalExceptionHandlerMiddleware → CORS → (no-producción) TestHeaderMiddleware → UseRouting → UseAuthorization → MapControllers.
  9. RoutePrefixFilter valida que el controlador/acción permita ese segmento de ruta; si no, 404.
  10. UsersController.Current (o el controlador OData correspondiente) se ejecuta: parsea X-UserSessionModel, resuelve el CustomerPublicTenant a partir de X-PublicTenant vía ICustomerPublicTenantService, y hace upsert del usuario local vía IUserService.UpsertFromSession.
  11. El servicio invoca al repositorio correspondiente, que usa DevPortalDbContext (EF Core/Npgsql) para ejecutar SQL contra PostgreSQL (contenedor dev-portal-postgres, puerto 5432).
  12. El resultado se mapea a un DTO (Mapperly, Api/Mappings/DtoMapper.cs) y se devuelve como JSON al frontend.
  13. El frontend actualiza el store Pinia y el router permite continuar la navegación, disparando más llamadas (ej. a controladores OData para listar tenants, productos, deployment requests), repitiendo el mismo patrón de los pasos 7–12 en cada operación de lectura/escritura.

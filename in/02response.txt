  4. ¿Es user: "1000:1000" portable y suficiente?
  
  Lo que el fix sí logra:
  - Elimina el único proceso que escribía en node_modules como UID 0. Desde ahora, todo lo que cree Vite pertenece a 1000.
  - En Windows y macOS, ese UID coincide con node del Dev Container. La prevención es completa para cualquier archivo nuevo.
  - Que Vite escuche en el puerto 80 sin ser root (adminUi/vite.config.ts:32) funciona porque Docker Engine 20.10 y posteriores fijan
  ip_unprivileged_port_start=0 dentro del contenedor. Ustedes ya lo confirmaron en la práctica.
  
  Riesgos reales:
  1. Hosts Linux o WSL con UID distinto de 1000. node del Dev Container pasaría a tener, por ejemplo, UID 1001, y los contenedores de UI
  seguirían escribiendo como 1000. El problema volvería con otro UID. No afecta a Windows abierto desde Windows.
  2. Volúmenes existentes. user: no corrige la propiedad de lo que root ya creó. Si un desarrollador tiene node_modules/.vite propiedad de
  root, el contenedor de UI (ahora 1000) puede fallar con EACCES al escribir ahí. Hace falta una limpieza única: sudo chown -R node:node sobre
  los node_modules afectados, o borrar .vite. sudo está disponible (postCreateCommand.sh:12).
  
  Ajuste opcional, solo si necesitan cubrir hosts Linux: parametrizar el valor como user: "${DEV_UID:-1000}:${DEV_GID:-1000}" y que
  detect-and-write-volume.sh escriba id -u e id -g en .env. Ese script ya regenera .env en cada arranque (línea 57). La alternativa,
  "updateRemoteUserUID": false, fija 1000 en todos los casos. Pero en hosts Linux con otro UID puede impedir leer archivos con permisos 600
  del bind mount /tmp/host-home (devcontainer.json:38), como el kubeconfig. Por eso no la recomiendo.
  
  Conclusión
  
  Conservamos el fix actual sin cambios. Ataca el mecanismo demostrable: un proceso con UID 0 (Vite en los contenedores de UI) creaba archivos
  en node_modules de un volumen que el Dev Container usa como UID 1000. Para Docker Desktop en Windows es portable y suficiente. La
  parametrización solo hace falta si alguien trabaja desde Linux o WSL con un UID distinto de 1000. Ese caso no rompe el fix; solo no lo
  cubre.
  
  Prevención demostrable frente a causa histórica:
  - Demostrable por código: después del fix, ningún proceso de este flujo escribe en node_modules del volumen compartido como UID 0. Este
  documento cubre la prevención de nuevos archivos, no la reparación de los existentes.
  - No identificada: qué archivos concretos causaron el EACCES histórico. Que fuera node_modules/.vite creado por root es coherente con el
  código actual, pero no está demostrado. Además, una versión anterior de Dockerfile.dev o del compose pudo ejecutar pnpm install como root.
  Lo confirmaría encontrar archivos con uid 0 en un volumen afectado, o una versión anterior de docker-compose-devui.yml o Dockerfile.dev en
  el historial de git.

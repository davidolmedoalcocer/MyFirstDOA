# Contexto y objetivo (lo que se pidió)

Se solicitó actuar como Sr. .NET/ASP.NET Core especializado en incidentes de producción, concurrencia, ThreadPool y `Microsoft.Data.SqlClient`, para el ticket:

> "Mitigación de disponibilidad: cambiar `db.Open()` por `await db.OpenAsync()` en los métodos async de SSOAPI"

sobre la rama `features/ssoapi-async-sql-and-request-observability`, sin modificar código, sin commits/push, sin cargar Production, separando hechos de inferencias, y entregando una propuesta técnica en el formato obligatorio pedido, esperando VoBo explícito antes de tocar cualquier archivo. Contexto: incidentes de producción 2026-09-01 y 2026-09-02 en `ds-web-ssoapi-prod` (cluster `rke2-prod-cluster-ws-04`, namespace `ngls-api`, pod `ds-web-ssoapi-864d7b6f79-jd4f8`), con bursts de tráfico contra `GET /SSOAdmin/GetEntitiesForApp?appID=117` (y el día 2 también `/Users/GetUser` → `GetUserPrefsAsync`), SQL Server respondiendo en ms mientras los spans HTTP/SqlClient tardaban 15-60s, error `Execution Timeout Expired`, ThreadPool saturado (workers hasta 308), y caída de `/health/liveness` que provocó el reinicio del pod.

No he modificado ningún archivo. Esta es la propuesta final, ya con la corrección que pediste verificar (el hallazgo de `/health/liveness` pasó de "inferencia" a "hecho de código confirmado", verificado con lectura determinística del pipeline y corroboración en Datadog).

---

## 1. Executive Summary

Propongo convertir `db.Open()` → `await db.OpenAsync()` en los ~30 métodos `async` de `SSOAdminRepository`, `SSOAuthRepository`, `GenericRepository` y `NotificationRepository` que abren una `SqlConnection` nueva por llamada. Está respaldado por: (a) el hallazgo de código confirmado (`db.Open()` síncrono dentro de métodos `async`, verificado línea por línea), (b) tu repro real-code (mismas versiones de Dapper/SqlClient) que reprodujo el mismo síntoma — `Timeout expired obtaining a connection from the pool`, p95≈35s, liveness caído — y lo resolvió solo cambiando a `OpenAsync`, y (c) que el propio código ya usa este patrón en `GetGroupDetails` (`await conn.OpenAsync()`), es decir no es un patrón nuevo para el equipo. Además, verificado ahora como **hecho de código** (no inferencia): `/health/liveness` pasa por el mismo middleware de logging fire-and-forget que el resto del tráfico, lo cual es coherente con que la caída de liveness ocurriera junto con la saturación general del ThreadPool. Hay 3 hallazgos adicionales con relación técnica directa que conviene decidir si entran en este PR o en uno separado: un `.Result` real (sync-over-async) en `ImportUser`, el logging fire-and-forget vía `Task.Factory.StartNew`, y una amplificación N×4 de `db.Open()` secuenciales en `SSOAuthRepository.GetUserAsync`.

## 2. Evidence Boundary

### FACTS CONFIRMED (incidente, dados por ti)
- Bursts de requests concurrentes el 2026-09-01 (`GetEntitiesForApp?appID=117`) y 2026-09-02 (`GetEntitiesForApp` + `/Users/GetUser` → `GetUserPrefsAsync` → `Dapper.QueryAsync`).
- SQL Server ejecutó `SSOGetEntitiesForApp` en ms (max 65ms el día 1; avg 20ms/max 130ms el día 2) mientras los spans HTTP/SqlClient duraron 15–60s.
- Error `SqlException: Execution Timeout Expired (-2, State 0, Class 11)`.
- Worker threads 5-6 → picos de 308; requests actuales ~313; conexiones actuales ~321; threads totales ~340.
- `/health/liveness` dejó de responder → 3 fallos consecutivos → Kubernetes reinició el pod.
- Repro local (harness fuera del repo, `ssoapi-incident-repro`) con Dapper 2.1.44 / Microsoft.Data.SqlClient 5.2.2, real-code contra SQL Server local: `db.Open()` sync → 187/3000 errores `InvalidOperationException: Timeout expired obtaining a connection from the pool`, p95=34.7s, liveness 4/4 fallidas, workers baseline~2.5→pico 108. `await db.OpenAsync()` → 0 errores, p95=437ms, liveness 92/92 OK, workers pico 11.

### CODE FACTS CONFIRMED (verificado leyendo el código línea por línea)
- `SSOAdminRepository.cs` `GetEntitiesForApp(long appID)`: `using SqlConnection db = new(_connectionString); db.Open(); ... return await db.QueryAsync<EntityModel>("SSOGetEntitiesForApp", ...)`. Coincide exactamente con el flujo reportado del incidente (`SSOAdminController.GetEntitiesForApp` → `SSOAdminService.GetEntitiesForApp` → este método).
- El mismo patrón (`db.Open()`/`conn.Open()` síncrono dentro de un método `async`) se repite en ~30 métodos de `SSOAdminRepository.cs`, `SSOAuthRepository.cs`, `GenericRepository.cs` y `NotificationRepository.cs`.
- `SSOAdminRepository.cs` línea 676: `return _accountService.ImportUser(ssouser.LoginName, false, ssouser.SiteID).Result;` dentro de un método **síncrono** `ImportUser`, invocado desde `SSOAdminController.ImportUser` (síncrono) → `SSOAdminService.ImportUser` (síncrono). Es `.Result` real sobre un `Task<string>` async.
- `SSOAdminRepository.cs` método `GetGroupDetails` **ya usa** `await conn.OpenAsync()` y `QueryMultipleAsync` — precedente ya existente en la base de código.
- `SSOAuthRepository.cs` `GetUserAsync`: por cada `app` en `userApps`, llama secuencialmente a `GetUserRolesAsync`, `GetUserOperationsAsync`, `GetUserTasksAsync`, `GetSSOLenderGroupsAsync`, y cada uno abre una `SqlConnection` **nueva** con `db.Open()` síncrono. Un usuario con N apps genera hasta 4×N aperturas síncronas secuenciales en una sola request.
- `SSOAuthRepository.cs` `GetSSOUserData`: usa `SqlDataAdapter.Fill(userData)` (ADO.NET síncrono/bloqueante) dentro de un método declarado `async Task<DataSet>` que nunca hace `await` real sobre esa llamada.
- `SSOAccountRepository.cs`: clase **completamente síncrona** (`IsEmailExists`, `GetUserPrefs` con `SqlDataReader`, `SetSSOUserData` con `db.Query`, `SetUserPrefs` con `conn.Execute`), usada desde `AccountService`.
- Common/Logging/LoggingService.cs: `LogRequestResponse` y ambos overloads de `LogError` usan `Task.Factory.StartNew(...)` (fire-and-forget, ThreadPool) sin `await`.
- **[Verificado y reclasificado tras tu observación]** `Program.cs`: `app.UseRequiredHeaderValidator(); app.UseRequestResponseLogging();` se registran como middleware global antes de `app.MapHealthChecks(...)`, sin ningún `MapWhen`/branch que excluya rutas. Esto es determinístico en ASP.NET Core: middleware registrado con `app.Use...()` antes de los `Map*` se ejecuta para **toda** request, incluidas las de `/health/liveness`, salvo que haya una rama explícita que lo excluya (no la hay). `RequiredHeaderValidatorMiddleware.cs` solo excluye paths con `/settings` o `/swagger`. `RequestResponseLogging.cs` solo excluye la llamada a `_trackguardLogger.LogRequestResponse(...)` para paths con `/ping` o `/swagger` — `/health/liveness` no cumple ninguna exclusión, así que **sí** dispara ese `Task.Factory.StartNew` fire-and-forget en cada probe de liveness. Confirmado por lectura de código, no por telemetría (ver más abajo por qué Datadog no puede probarlo para las llamadas que fallaron).
- `builder.Services.AddHealthChecks();` (Program.cs) no registra ningún `IHealthCheck` con tag `"monitor"` (usado por el predicate de `/health/liveness`) — el endpoint en sí no hace ningún trabajo de dependencia (no pinga SQL).
- Connection string SSO no define `Max Pool Size` ni `Connect Timeout` explícitos → aplican defaults de Microsoft.Data.SqlClient (Max Pool Size=100, Connect Timeout=15s).
- `ADWrapper.cs` `ValidateCredentials`: bind LDAP **síncrono** (`Novell.Directory.Ldap`), usado en el flujo de autenticación.

### INFERENCES (plausibles, no medidas/cuantificadas)
- Que el logging fire-and-forget (`Task.Factory.StartNew`) en cada request/probe **haya contribuido de forma medible** a la saturación del ThreadPool durante el burst es razonable pero no está cuantificado — no sé cuánto retraso añade bajo esa carga específica sin reproducirlo.
- La amplificación N×4 en `GetUserAsync` (SSOAuthRepository) podría explicar por qué `/Users/GetUser` también falló el 2 de septiembre, pero no tengo el dato de cuántas apps tenía asignado el usuario afectado ese día.

### UNKNOWN / NEEDS CONFIRMATION
- **Sobre `/health/liveness` y Datadog**: busqué spans (`service:ds-web-ssoapi-prod resource_name:*health*`) filtrando por el pod exacto (`ds-web-ssoapi-864d7b6f79-jd4f8`) en la ventana 08:00–08:20 UTC del 2026-09-01. Encontré solo 3 spans de liveness en esa ventana (uno con `useragent: kube-probe/1.34` a las 08:09:42, 2.3ms, status 200), y **ninguno cae dentro de las ventanas de falla exactas** (08:07:42–08:08:13 y 08:13:27–08:13:58 UTC). Búsqueda de logs (`*health* OR *liveness*`) en ambos días: 0 resultados. Esto es un límite esperado de la telemetría (los probes que realmente fallaron probablemente no generaron un span completo, y los logs Serilog/TrackGuard de la app no se ingieren en Datadog Logs, gap ya documentado) — **no contradice ni confirma** el mecanismo por esa vía; la confirmación válida es la lectura de código de arriba.
- No se localizó ningún `CommandTimeout` explícito en el código (usa el default de Dapper/SqlCommand, ~30s).
- No se verificó `ThreadPool.SetMinThreads` ni variables de entorno de runtime en el Dockerfile/k8s yaml de producción.
- No confirmé si `AuthenticationController`/login tuvo tráfico relevante durante el incidente (relacionado al hallazgo de LDAP síncrono).

## 6. Scope / PR Plan

- **Branch/PR**: `features/ssoapi-async-sql-and-request-observability` (ya estás en ella) o, si prefieres separarlo, `fix/ssoapi-sync-sqlconnection-open`.
- **Título sugerido**: "Fix: reemplazar `db.Open()` síncrono por `await db.OpenAsync()` en repositorios async de SSOAPI".
- **Descripción corta**: Mitigación de disponibilidad para el incidente de producción 2026-09-01/02. Bajo bursts de concurrencia, `db.Open()` síncrono dentro de métodos `async` retiene workers del ThreadPool esperando adquirir conexiones del pool, lo que en producción derivó en timeouts de SqlClient (aunque SQL Server respondía en ms) y coincidió con la caída de `/health/liveness`. Se reemplaza por `await db.OpenAsync()` donde es seguro hacerlo sin tocar transacciones ni firmas públicas.
- **Archivos esperados**: `SSOAdminRepository.cs`, `SSOAuthRepository.cs`, `GenericRepository.cs`, `NotificationRepository.cs`.
- **Explícitamente fuera de alcance**: `SSOAccountRepository.cs`, `CMSWrapper.cs`, `ChangeEntityAssignments`, `GetSSOUserData`, el `.Result` en `ImportUser`, el logging fire-and-forget de `LoggingService`, el orden de middlewares en `Program.cs`, y `ADWrapper.ValidateCredentials`.

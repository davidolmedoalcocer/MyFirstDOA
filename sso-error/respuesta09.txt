## 1. ROOT CAUSE

**Causa raíz: ráfaga de solicitudes concurrentes contra `GET /SSOAdmin/GetEntitiesForApp?appID=117`, todas compartiendo el mismo `trace_id`, que saturó el ThreadPool/pool de conexiones de .NET del pod — no un problema de SQL Server.**

**Estado: CONFIRMADA** (evidencia cuantitativa, no solo correlación — ver cadena causal abajo).

Evidencia concreta:
- SQL Server ejecutó `SSOGetEntitiesForApp` (query_id=41422/plan_id=3007) en **milisegundos** durante todo el incidente (Query Store, verificado por mí): 08:00–08:30 UTC → 401 ejecuciones, avg=10.9ms, **max=64.9ms**, avg CPU=5.9ms, max CPU=16.5ms.
- `sys.query_store_wait_stats` para ese plan: únicamente categorías **CPU** y **Memory** (max 58ms y 5ms respectivamente). Cero Lock/Latch/Buffer IO/Network IO/Worker Thread.
- **216 solicitudes** HTTP a ese endpoint entre 08:07–08:13 UTC, con `status:500`, **TODAS con el mismo `trace_id` (`6a96872b...`)** — verificado con `aggregate_spans` (`distinct_traces=1` en cada bucket de 1 minuto). Esto es anómalo: implica que un único caller (o un componente que reutiliza el contexto de traza) generó decenas de llamadas concurrentes/reintentos sin regenerar el trace-id.
- Métrica `runtime.dotnet.threads.workers_count` del pod afectado (`jd4f8`) muestra un salto abrupto de **4 → 49 hilos** exactamente a partir de **08:07:00 UTC** (el mismo minuto del primer burst), y un segundo salto **hasta 60 hilos** hacia 08:13–08:14 UTC (segundo burst). El pod gemelo (`d45vs`, no afectado) se mantuvo plano en ~4 hilos todo el tiempo. Este patrón de rampa gradual (4→14→22.75→31.5→40.25→49) es la firma clásica de **ThreadPool starvation** con inyección throttled de workers, NO de tráfico normal.
- `queue_length` (cola de Kestrel) = 0 todo el tiempo → confirma que el cuello de botella no era la cola HTTP de entrada, sino los hilos ya en ejecución bloqueándose (consistente con `db.Open()` síncrono dentro de rutas async).

## 3. WHAT ACTUALLY HAPPENED (técnico, ≤10 líneas)

Un caller (no identificable con certeza) disparó decenas de llamadas concurrentes a `GetEntitiesForApp(appID=117)` reutilizando el mismo contexto de traza — indicio de un retry sin backoff ni regeneración de correlación. Cada llamada abre una `SqlConnection` con `db.Open()` **síncrono** dentro de un método `async`, compartiendo el mismo pool que usa toda la API. La concurrencia repentina saturó el ThreadPool de .NET (workers 4→49→60), lo que retrasó la ejecución de continuaciones async — incluido el temporizador interno de SqlClient que dispara "Execution Timeout Expired" y el propio endpoint `/health/liveness`. SQL Server, mientras tanto, ejecutó la consulta real en <65ms; el "timeout" fue enteramente client-side/scheduling, no de base de datos. Al no responder liveness a tiempo, Kubernetes mató y reinició el pod (consecuencia, no causa). El ciclo se repitió ~5 minutos después porque el caller siguió reintentando.

## 5. CODE CORRELATION

- `SSOAdminRepository.cs:362-369` — `GetEntitiesForApp`: `using SqlConnection db = new(_connectionString); db.Open();` — **apertura síncrona dentro de un método `async`**, sin `CommandTimeout` explícito (usa el default de 30s de `SqlCommand`, coincide con los ~35-38s observados sumando latencia de scheduling).
- Este patrón (`db.Open()` síncrono) se repite en **todos** los métodos de `SSOAdminRepository.cs`, `SSOAccountRepository.cs`, `GenericRepository.cs`, `NotificationRepository.cs`, `SSOAuthRepository.cs` — todos comparten el mismo pool (`SSODBConnectionString`), por lo que un burst en un endpoint puede saturar recursos usados por todos los demás.
- `ConnectionManager.cs` y `appsettings.json` no configuran `Command Timeout` ni `Max Pool Size` en la cadena de conexión → todos los defaults de ADO.NET aplican (30s comando / 15s pool).

## 6. FIX

**Necesario para este incidente (una vez que se identifique y corrija al caller):**
- Nada del lado de SSOAPI corrige la causa raíz real (el caller retransmitiendo sin backoff); se necesita identificar y arreglar ese caller primero (ver GAPS).

**Mejoras secundarias encontradas (NO causaron este incidente, pero mitigarían recurrencias):**
- Cambiar `db.Open()` → `await db.OpenAsync()` en todos los repositorios para no bloquear hilos del ThreadPool durante picos de concurrencia.
- Configurar `CommandTimeout` explícito y razonable en las llamadas Dapper (hoy usa el default de 30s silenciosamente).
- Añadir `Max Pool Size` explícito y monitoreo del pool (`SqlClientEventSource` / `System.Data.SqlClient.EventCounters`) para detectar agotamiento antes de que cause timeouts.
- Añadir *circuit breaker* / *rate limiting* por endpoint para evitar que un caller descontrolado degrade todo el servicio.
- Investigar por qué múltiples requests comparten el mismo `trace_id` (posible bug de instrumentación en el caller o en un proxy intermedio) — esto además **contamina el diagnóstico** en Datadog.

## 7. HOW TO PROVE THE FIX

1. Reproducir en un entorno de carga: disparar 50-100 requests concurrentes a `GetEntitiesForApp` contra un pod con límites de recursos similares a prod.
2. Confirmar que **sin** el fix, `runtime.dotnet.threads.workers_count` se dispara igual que en prod y aparecen `Execution Timeout Expired` pese a que SQL Server sigue respondiendo en ms.
3. Aplicar `OpenAsync` + límite de concurrencia/circuit breaker.
4. Repetir la misma carga y verificar que `workers_count` se mantiene estable, no hay HTTP 500, y `/health/liveness` sigue respondiendo bajo carga.

## 8. MESSAGE FOR CHARLES

> We root-caused the Sept 1 SSOAPI outage (08:05–08:15 UTC). SQL Server itself was never the problem — Query Store shows `SSOGetEntitiesForApp` executing in under 65ms the entire time, with zero lock/latch waits. Instead, 216 calls to `GetEntitiesForApp?appID=117` hit the pod in two ~1-minute bursts, all sharing the exact same trace ID — strong evidence of a caller retrying without backoff or trace regeneration. This concurrency spike saturated the .NET ThreadPool (worker count jumped from 4 to 49, then 60), which delayed everything on the pod, including the SQL client's own timeout callback (hence the misleading "Execution Timeout Expired" at 35-38s) and the `/health/liveness` endpoint. Kubernetes then killed and restarted the pod after 3 consecutive liveness failures — that restart was a *consequence*, not the cause. We couldn't identify the calling application from Datadog/app logs (no caller IP/User-Agent captured for these specific requests). Proposal: (1) find and fix the retry loop/caller, (2) as defense-in-depth, switch SSOAPI's `db.Open()` calls to async and add basic rate limiting/circuit breaking so one noisy caller can't take down the whole pod again.

## 9. GAPS

- **Identidad exacta del caller**: no se pudo determinar quién generó el burst. Datadog no capturó IP/User-Agent en los spans de este endpoint, y los logs de aplicación (Serilog) del pod en esa ventana solo contienen logs de arranque (post-restart), no logs de request. **Cómo obtenerlo ahora**: revisar logs del *reverse proxy / ingress* (nginx/traefik) delante de `sso-api.appsprod.ngls.ngic.com` si retienen client IP y User-Agent por más tiempo; o revisar logs de la aplicación TGLD (si Charles tiene acceso) para su propio historial de llamadas/reintentos en esa ventana.
- **Confirmación del mensaje exacto de excepción del span de ~15.08s** (08:13:15–08:13:30): no se verificó si corresponde a "pool timeout" (15s) vs otra causa; requeriría expandir ese span puntual en Datadog (`get_datadog_trace` sobre ese sub-span específico).
- **CPU throttling real**: no tengo acceso al manifiesto de Kubernetes con los `resources.limits.cpu` reales del pod (el `.k8s.yml` en este repo es el pipeline de build, no el manifiesto de despliegue) — sin ese límite no puedo confirmar si el pico de ~207 millicores representó throttling real o quedó lejos del límite.
- **Network Performance Monitoring** entre el pod y `LWVPDBSQLA020.ngls.ngic.com`: no encontré métricas de NPM en las consultas realizadas — no puedo confirmar si existía telemetría de red habilitada; si no lo está, no hay forma de descartar por completo un componente de red sin acceso a esa configuración de Datadog.

### 2. ¿`SqlConnection`/`SqlCommand`/`SqlDataReader`/`SqlTransaction` quedan garantizadamente disposed en éxito y en excepción?

**HECHO** — En **todas** las 63 ubicaciones que crean `SqlConnection`, se usa `using` (ya sea declaración `using SqlConnection x = new(...)` estilo C# 8, o bloque `using (...)  { }`). Una declaración `using` en C# garantiza `Dispose()` al salir del scope **tanto en éxito como por excepción** (el compilador genera un `try/finally` implícito), así que a nivel de `SqlConnection` no encontré ninguna fuga garantizada.

Casos puntuales revisados:
- `SSOAccountRepository.GetUserPrefs`: `SqlCommand` y `SqlDataReader` también están en `using` → disposal garantizado.
- `SSOAdminRepository.ChangeEntityAssignments`: `SqlTransaction` en `using`, con `try { ... trans.Commit(); } catch { trans.Rollback(); throw; }` → correcto, hace rollback antes de relanzar y el `using` libera `trans`/`conn` igual.
- `SSOAuthRepository.GetSSOUserData`: usa `SqlDataAdapter` con `using`, y no llama `Open()` explícito — el adapter abre/cierra la conexión automáticamente durante `Fill()` (comportamiento estándar de ADO.NET). Correcto.
- `SSOAdminRepository.GetGroupDetails`: única ubicación con `await conn.OpenAsync()` + `QueryMultipleAsync` (patrón 100% async correcto), usando `using` también.

**Conclusión de este punto: HECHO — no hay fugas de disposal por falta de `using`.** El disposal en sí **no es la causa** de los timeouts.

### 4. `SqlDataReader`/`SqlTransaction` que puedan mantener una conexión ocupada más de lo necesario

**HECHO (hallazgo real, no hipotético)** — En `SSOAuthRepository.cs`, el método `GetUserAsync` mantiene la conexión `db` abierta durante **todo el método**, incluido un `foreach` sobre las aplicaciones del usuario que, en cada iteración, abre y cierra **4 conexiones adicionales** (`GetUserRolesAsync`, `GetUserOperationsAsync`, `GetUserTasksAsync`, `GetSSOLenderGroupsAsync`):

```csharp
using SqlConnection db = new(_connectionString);
db.Open();
...
var userApps = await db.QueryAsync<ApplicationModel>(...);   // db ya no se necesita después de esta línea

foreach (var a in userApps)
{
    var roles = await GetUserRolesAsync(loginName, a.ApplicationID);        // abre/cierra su propia conexión
    var operations = await GetUserOperationsAsync(loginName, a.ApplicationID); // abre/cierra su propia conexión
    var tasks = await GetUserTasksAsync(loginName, a.ApplicationID);          // abre/cierra su propia conexión
    app.SSOLenderGroups = await GetSSOLenderGroupsAsync(loginName, a.ApplicationID); // abre/cierra su propia conexión
    ...
}
// "db" sigue abierta aquí, sin usarse, hasta el "return" al final del método
```

`db` queda abierta (ocupando un slot del pool) durante todo ese bucle aunque ya no se use después del primer `QueryAsync`. Si un usuario tiene N aplicaciones, esto genera `1 + 4×N` conexiones adquiridas/cerradas por una sola llamada a `GetUserAsync`, más 1 conexión ociosa retenida innecesariamente todo ese tiempo.

Además, en `AccountService.cs` (`CreateUser`), la conexión `dbResult` queda abierta mientras se ejecuta `SendMailNotice(...)` (llamada SMTP de red) y una llamada anidada a `SetUserPrefs` (que abre otra conexión más) — es decir, una conexión SQL se mantiene abierta durante una operación de red no relacionada con la base de datos.

**Clasificación: HECHO** — patrón real de conexión retenida más tiempo del necesario. No hay `SqlDataReader` sin cerrar (todos están en `using`), el problema es de **alcance/scope de la conexión**, no de disposal.

### 9. Patrones que podrían provocar *pool exhaustion* aunque `GetEntitiesForApp` use `using` correctamente

**POSIBLE RIESGO** (no confirmado con telemetría de pool, pero sí demostrado en código):

- **Todos los endpoints de SSOApi comparten el mismo pool** (`SSODBConnectionString`) — no hay aislamiento entre el tráfico de autenticación/login (`SSOAuthRepository`, probablemente de alto volumen) y el tráfico administrativo (`SSOAdminRepository.GetEntitiesForApp`). Un pico de tráfico en login/tokens puede agotar el pool y afectar a `GetEntitiesForApp` aunque esta última esté perfectamente escrita.
- **`SSOAuthRepository.GetUserAsync`** (punto 4) multiplica el número de conexiones abiertas por cada llamada (`1 + 4×N` conexiones) y retiene una conexión más tiempo del necesario. Si este método se invoca en cada login/validación de token, bajo carga concurrente puede generar una **tasa de adquisición de conexiones muy alta** contra el mismo pool.
- **64 de 65 aperturas de conexión en la solución son síncronas (`.Open()`)**, no `OpenAsync()` (ver punto 10). Una apertura síncrona bloquea el hilo del pool de ASP.NET Core mientras espera turno para una conexión física o para completar el handshake TCP/TLS — bajo presión de pool, ese hilo queda bloqueado en vez de liberarse, lo que puede agravar la contención de hilos además de la de conexiones.
- No hay diferenciación de `Application Name` por repositorio/endpoint en la cadena de conexión (no se ve en el código un `Application Name=` distinto por servicio), lo que dificultaría diagnosticar en SQL Server *(vía `sys.dm_exec_sessions`)* qué componente concreto está consumiendo conexiones en un momento dado.

**No until encontré evidencia directa (contadores de pool, `SqlClientEventSource`, logs de `System.InvalidOperationException: Timeout expired. The timeout period elapsed prior to obtaining a connection from the pool`) de que el pool se haya agotado realmente el 2026-09-01 08:07-08:13 UTC** — eso requeriría telemetría del lado .NET (APM/Datadog) que no está disponible en el código fuente.

### 5. ¿Podemos identificar qué sesión/procedimiento bloqueaba `SSOGetEntitiesForApp` durante el incidente?

**No.** No existe ninguna fuente de datos disponible que permita reconstruir, a esta distancia en el tiempo, qué sesión específica pudo haber bloqueado la ejecución el 2026-09-01 a las 08:07–08:13 UTC:
- `sys.dm_exec_requests` / `sys.dm_tran_locks` solo reflejan el estado **actual** del servidor, no tienen retención histórica.
- `blocked process threshold (s) = 0` significa que SQL Server **nunca capturó** ese evento, ni ese día ni ningún otro — no es que se haya perdido el dato, es que nunca se generó.
- Query Store no registra qué sesión bloqueó a cuál; solo agrega duración/CPU/IO por consulta.

### 6. Conclusión explícita

**No hay evidencia histórica suficiente para demostrar que hubo bloqueo dentro de SQL Server durante el incidente — y, de hecho, la evidencia disponible apunta en contra de esa hipótesis, no a favor.** Concretamente:

- Query Store muestra que, exactamente durante la ventana del incidente (08:00–08:30 UTC) y también en la ventana previa (07:30–08:00 UTC), las 583 ejecuciones registradas de `SSOGetEntitiesForApp` tardaron entre ~6 ms y ~65 ms, todas clasificadas como `Regular` (ninguna `Aborted`).
- A lo largo de todo el día no aparece ninguna ejecución con duración cercana a los 35-37 segundos reportados por Datadog, ni ninguna ejecución cancelada/abortada.
- Los 6 deadlocks capturados ese día son ajenos por completo (otra base de datos, otros procedimientos, otros horarios).

**Importante — lo que esto NO descarta:** como `blocked process threshold = 0`, SQL Server nunca habría generado un `blocked_process_report` aunque el bloqueo hubiera ocurrido, así que esa ausencia específica no prueba nada por sí sola. Pero la ausencia de una duración elevada o de una ejecución `Aborted` en Query Store **sí es una señal más fuerte**, porque Query Store mide el tiempo real transcurrido de cada ejecución (incluyendo esperas de lock) independientemente de si esa función de auditoría de bloqueos está activada o no. Si `SSOGetEntitiesForApp` hubiera estado 35 segundos esperando un lock antes de completarse o ser cancelada, debería haber quedado reflejado ahí, y no aparece.

Dado esto, no debe concluirse que el bloqueo en SQL Server fue la causa — la evidencia recolectada sugiere que hay que buscar la causa en otra capa (por ejemplo, en el tiempo transcurrido antes de que la consulta llegara al motor de SQL Server: apertura de conexión, pool de conexiones, red, etc., que quedó documentado en la investigación anterior del lado .NET), pero eso requeriría datos de APM/Datadog a nivel de traza (tiempo de apertura de conexión vs. tiempo de ejecución del comando) que no están disponibles desde SQL Server.

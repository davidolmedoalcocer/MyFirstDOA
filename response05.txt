## HECHOS CONFIRMADOS

### 1. "Sequence contains no elements" — ruta confirmada

**Archivo:** CookieAuthenticationService.cs  
**Método:** `GetUserRoles()`, línea 51:
```csharp
var application = userSession.Applications.First(app => app.ApplicationID == 117);
```
Lanza `InvalidOperationException: "Sequence contains no elements"` cuando SSO devuelve HTTP 200 con un usuario cuya lista `Applications` no contiene `ApplicationID = 117`. Esto ocurre porque `SSOApi/AuthenticationController.Login` filtra la lista antes de responder: si el usuario no tiene app 117, la lista queda vacía.

**Esta excepción SÍ está capturada** por el bloque `catch (Exception ex)` en Program.cs, que hace redirect a `/login?error=Sequence+contains+no+elements`. No crashea el pod.

Sin embargo, con PW018 (HTTP 400), `SSOService.Authenticate` devuelve `null` antes de llegar a `GetUserRoles`, así que esta excepción **no se dispara en el camino PW018**.

---

### 2. NullReferenceException — ruta latente en componentes Blazor

En al menos 8 componentes, el patrón es:
```csharp
var INumber = user.Claims.FirstOrDefault(c => c.Type == "userid").Value;
```
— CookieHandlerControl.razor  
— VerifyControlBase.razor  
— ConfidenceReport.razor  
— SiteAccessManagement.razor  
— (más instancias similares)

Si `FirstOrDefault` retorna `null` (claim `"userid"` ausente), `.Value` lanza `NullReferenceException`. Estos están dentro del bloque `if (user.Identity is not null && user.Identity.IsAuthenticated)`, así que solo se ejecutan para usuarios autenticados. En el flujo normal el claim siempre se añade en `GetUserRoles`; el riesgo surge si el claim es missing por otro motivo (cookie corrupta, desincronización). En Blazor Server esta excepción derrumba el circuit, no el proceso.

### 3. Bug crítico de case-mismatch en SessionValidationMiddleware

**Archivo:** SessionValidationMiddleware.cs  
**Claim almacenado en** CookieAuthenticationService.cs:
```csharp
new Claim("sessionid", userSession.SessionId)        // lowercase 'i'
```
**Claim buscado en el middleware:**
```csharp
var sessionId = context.User.FindFirst("sessionId")?.Value;   // capital 'I'
```
`ClaimsPrincipal.FindFirst` es **case-sensitive** para tipos custom. El resultado: `sessionId` siempre es `null` para cualquier usuario autenticado.

**Consecuencia:** UserSessionHandler.cs:
```csharp
if (string.IsNullOrEmpty(userId) || string.IsNullOrEmpty(sessionId))
    return false;
```
`IsSessionValid` retorna `false` siempre → el middleware firma out al usuario en cada request HTTP → redirect a `/login?error=session_expired` → el usuario ve "Your session started in another browser" inmediatamente después de un login exitoso.

### 4. HttpClient sin timeout en SSOService

**Archivo:** SSOService.cs

Ninguno de los dos constructores de `SSOService` configura `_httpClient.Timeout`. El timeout por defecto de `HttpClient` es **100 segundos**. Si SSOApi está lento o inalcanzable, cada intento de login cuelga 100 s. La excepción resultante `TaskCanceledException` sí es capturada por Program.cs. No crashea el pod, pero acumula resources.

Adicionalmente, `SSOService` hace `new HttpClient()` por instancia y nunca lo dispone. Al ser registrado como `AddScoped`, cada circuit de Blazor crea un `HttpClient` nuevo. Estos no se disponen hasta que el GC los recolecta, acumulando sockets en estado TIME_WAIT.

---

### 5. Worker.ExecuteAsync sin try-catch

**Archivo:** Worker.cs

El bucle principal de `Worker.ExecuteAsync` no tiene `try-catch`. En .NET 8, el comportamiento por defecto de `BackgroundServiceExceptionBehavior` es `StopHost`: si cualquier excepción no-`OperationCanceledException` escapa de `ExecuteAsync`, **el host para, el proceso sale, y Kubernetes reinicia el pod**. El Worker no llama a SSO directamente, pero si la base de datos falla durante el ciclo de 5 minutos, el pod se reinicia.

---

### 6. async void sin manejo de excepciones

Hay 40+ métodos `async void` en componentes Blazor. Los más peligrosos:

— DocumentSelector.razor: contiene `user.First()` en L237 que lanza si el lookup de usuario devuelve lista vacía.  
— AuditManagement.razor: `users.First(u => u.INumber... == CurrentLoggedUser...)` lanza si el usuario no está en la lista.

En Blazor Server, excepciones en `async void` dentro del circuit context van al circuit error handler → circuit se derrumba. El pod NO crashea. Pero si la excepción escapa del circuit (p. ej., desde un thread pool thread sin SynchronizationContext de Blazor), va a `AppDomain.UnhandledException` y puede terminar el proceso.

## CAUSA DE LA CASCADA

El ciclo destructivo confirmado por el código:

```
Login exitoso (SSO responde 200)
         ↓
GetUserRoles() ejecuta y añade claim "sessionid" (minúscula)
         ↓
Cookie generada con claim "sessionid"
         ↓
Usuario redirigido a /login-sucsess → carga cualquier página
         ↓
SessionValidationMiddleware: FindFirst("sessionId") → null (case mismatch)
         ↓
IsSessionValid(username, null) → false (línea 32 UserSessionHandler)
         ↓
context.SignOutAsync() → cookie eliminada
         ↓
Redirect → /login?error=session_expired
         ↓
Usuario reintenta login → nuevo intento a SSO → ...loop
```

Si SSO está lento (no solo PW018 sino network latency), cada iteración del loop añade una request colgada de hasta 100 s. Con múltiples usuarios simultáneos:
- Sockets acumulados (HttpClient sin dispose, sin IHttpClientFactory)
- Memoria acumulada (objetos de respuesta pendientes)
- Presión gradual → OOM → **pod reiniciado por el kubelet**

El segundo mecanismo de reinicio independiente: cualquier excepción SQL en `Worker.ExecuteAsync` → host para → pod reiniciado por K8s.

  Origen de la columna "obligatorio": no se puede verificar desde el repositorio, porque no hay reglas de rama versionadas. Lo comprobé con gh api
  repos/infios-tools/dev-portal/rulesets/8889824. El ruleset "Pull request" está activo sobre ~DEFAULT_BRANCH (hoy origin/HEAD es develop), release/** y

  cambiar sin pasar por un commit.
  
  Lo que esto implica:
  
  - Las pruebas de sharedUIComponents y su diff-cover del 90 % corren en el PR pero no bloquean. Además hay dos jobs con el mismo nombre de check (ci.yml:11 y
  :261), y uno de ellos duplica al otro sin cobertura.
  - Ningún Playwright bloquea el merge, ni el de API ni el de UI.
  - No hay integración contra Postgres real en ningún check obligatorio. Esa capa solo existe en el job E2E, que es informativo.
  
  4. Desarrollo, PR y después
  
  Durante el desarrollo, un desarrollador puede ejecutar todas las capas en local:
  
  - Unitarias e integración en proceso de la API con dotnet test (sin documentar para desarrolladores, README.md:68).
  - Vitest en los tres proyectos de frontend, incluido el modo watch en sharedUIComponents (package.json:21).
  - Playwright API y UI contra el stack de testing en Docker, filtrando por ID de work item con -g (e2e/README.md:18, :71).
  
  Ningún hook ni documento exige ejecutarlas antes del PR.
  
  En el PR corren todas las suites anteriores, incluido el Playwright completo (ci.yml:410-465). Solo bloquean API (.NET), Admin UI y Tenant UI con sus
  umbrales de cobertura. Shared UI y E2E son informativos. La parte de "bloquea" sale del ruleset de GitHub, no del repo.
  
  Después del merge, según la documentación del repo:
  
  - Un push a develop o release/** vuelve a ejecutar ci.yml (:3-4), incluido E2E. También ejecuta cd.yml (:2-7), que construye las imágenes, las escanea con
  Wiz y las publica, sin ejecutar pruebas (cd.yml:21-228, solo hay pasos de build, scan y push).
  - Un tag v* ejecuta release-promotion.yml (:3-5, :22), que solo re-etiqueta y promociona imágenes a OCIR (:74-108), sin pruebas.
  - El repo no documenta regresión manual, smoke tras el despliegue, firma de QA ni pruebas en un entorno desplegado. Esto queda como no verificado. Hay
  indicios de que existen fuera del repo, pero no de cuándo se ejecutan:
    - Plan de pruebas manuales en ADO, que e2e/fetchAdoTests.mjs descarga como contexto de automatización (e2e/README.md:74-87).
    - Etiqueta @Regression en un solo test (Tenants.test.ts:11), que ninguna configuración ni workflow filtra.
    - El ADR 004 menciona datasets de "developer/QA" (adr-004-product-version-and-build-model.md:148).
  
  Para comparar con Automation First: hoy las pruebas automáticas existen en todas las capas, pero las únicas que cierran el paso al merge son las unitarias e
  integración en proceso de API, adminUi y tenantUi. Para que Playwright bloquee haría falta convertir el check E2E (Playwright) en obligatorio, que es lo que
  tiene pendiente la PBI 507927.

• Settings: arquitectura, recorrido de la petición y pruebas, con una sola acción
  
  Uso la acción "un administrador abre Settings y ve la pestaña Configurations". Esa pantalla sí llama a OData y llega a PostgreSQL, y tiene pruebas en varias capas. Lo
  más importante: no existe una prueba de API para la consulta que lista los Settings. Hoy la única prueba que recorre el camino completo hasta la base es la de
  Playwright. Todo esto sale de leer el código y el historial de git. No ejecuté ninguna prueba.
  
  ───────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────────
  
  1. Mapa de la arquitectura
  
  Primero, unos términos:
  - Dev Container: el contenedor donde corre tu VS Code, con pnpm, .NET, kubectl y el cliente de Docker.
  - SPA (Single Page Application): una aplicación web que se descarga una vez y después cambia de pantalla sin recargar la página.
  - OData: una convención para APIs REST en la que los filtros, el orden y las relaciones viajan en la URL, como $filter, $orderby y $expand.
  - nginx: un servidor web que entrega archivos y puede reenviar peticiones a otro servidor. A eso se le llama proxy.
  - Kong: el gateway de la plataforma que, en Kubernetes, recibe las peticiones y les añade la identidad del usuario.
  
  Qué es cada parte del frontend
  
  - adminUi: la SPA para administradores. Llama al segmento /admin del servicio.
  - tenantUi: la SPA para clientes. Llama al segmento /customer.
  - sharedUIComponents: no corre por su cuenta. Es código compartido (componentes Vue, stores, servicios y cliente HTTP) que cada UI importa como código fuente con el
  alias @devportal/shared-ui (adminUi/vite.config.ts). Las pantallas viven aquí. Por ejemplo, adminUi/src/views/SettingDashboardView.vue solo envuelve a
  SettingDashboard.vue de sharedUIComponents.
  
  Entorno local de desarrollo (tareas "Dev: Start Services" y "Dev: Start UI")
  
   Tu navegador (fuera de los contenedores)
     │  abre http://localhost:35001/devportal/adminui
     ▼
   [contenedor dev-portal-admin-ui]  vite dev (pnpm dev), puerto 35001
     │  el JS del navegador llama DIRECTO a http://localhost:35000/admin/odata/...
     ▼
   [contenedor dev-portal-service]   dotnet watch run, Development, puerto 35000
     │  EF Core + Npgsql
     ▼
   [contenedor dev-portal-postgres]  PostgreSQL 16, puerto 5432
        ▲ el esquema lo crea [dev-portal-liquibase] una vez al arrancar
  
   [Dev Container]: VS Code, pnpm install, docker CLI. No corre la app.
  
  - El Dev Container usa docker-outside-of-docker (.devcontainer/devcontainer.json). Los contenedores de la app los lanza el Docker de tu máquina y corren al lado del
  Dev Container, no dentro. Montan el mismo volumen del workspace (docker-compose.yml, docker-compose-devui.yml).
  - La dirección del backend viene de adminUi/index.html. En modo dev nadie reemplaza $BACKEND_SERVICE_URL, así que se usa el valor por defecto
  http://localhost:35000/admin. Como el navegador llama a otro puerto, el servicio permite ese origen en la lista de CORS
  (devPortalService/src/appsettings.Development.json). CORS es la regla del navegador que bloquea llamadas a otro origen salvo que el servidor las autorice.
  - No hay login real. TestHeaderMiddleware.cs añade el usuario test-user cuando la petición no trae el header X-UserSessionModel, en cualquier entorno que no sea
  Production.
  - Si tienes un clúster Kubernetes local, configure-k8s-services.sh aplica ingresses de Kong que publican /devportal/service/admin con el header X-Route-Segment: admin
  (k8s/dev-portal-route-segment-admin-portal.yaml). No seguí cuándo usa ese camino la UI de dev. Con la configuración por defecto, la UI llama directo al puerto 35000.

  Tres diferencias con dev cambian el recorrido:
  1. En pruebas, la UI llama a su mismo origen y nginx reenvía la petición. entrypoint.sh pone BACKEND_SERVICE_URL=/devportal/service/admin. Como el origen es el mismo,
  CORS no interviene.
  2. La UI es un build compilado servido por nginx, no vite en modo dev.
  3. El servicio corre en modo Testing. Un middleware adicional en Program.cs (línea 157) pone el tenant test-devportal y el usuario test-user. El login de la SPA se
  salta con VITE_TESTING (sharedUIComponents/src/auth/auth.ts, adminUi/src/router/index.ts).

  2. La petición de ida y vuelta
  
  Qué intenta hacer la persona: revisar el catálogo de Settings de configuración y ver, para cada uno, de dónde saca su valor. Eso es la columna Resolution, por ejemplo
  Expression: true o Generated: Type = Base64, Length = 32.
  
  La petición
  
  Es un GET a:
  
  {backend}/odata/settings
    ?$expand=settingVersions($select=id,settingId,revisionNumber,manifestPlacement,valueStrategy,
                             valueExpression,generatedFormat,generatedLength,vaultKeyExpression,vaultIdExpression)
    &$orderby=key
  
  {backend} depende del entorno:
  - Dev: http://localhost:35000/admin
  - Pruebas: /devportal/service/admin en el origen de la UI. nginx lo reenvía a http://dev-portal-service-testing:8080/admin/odata/settings?...
  
  El navegador codifica los caracteres especiales, así que $ viaja como %24, y así sucesivamente.
  
  Los dos parámetros significan:
  - $expand trae, junto a cada Setting, sus revisiones (settingVersions) con solo esos campos.
  - $orderby=key ordena por la clave.

  3. Las pruebas sobre ese mismo recorrido
  
  Términos de esta sección:
  - Unit / componente: pruebas que corren en Node, sin servidor. Usan Vitest en el frontend y xUnit en el backend.
  - mock: una pieza falsa que responde lo que la prueba le indica.
  - happy-dom: un DOM simulado sin navegador real. Lo usa Vitest en sharedUIComponents.
  - Base InMemory: el proveedor de EF que guarda los datos en memoria y no ejecuta SQL.

  Qué enseña esto sobre cada capa
  
  - Cuándo basta la unitaria: para el formato de Resolution, el filtro por placement y qué parámetros manda el frontend. Es lógica que no depende del servidor, y ya está
  bien cubierta.
  - Por qué una prueba de API necesita la base aunque corra en Docker: Docker es solo el lugar donde corre. Lo que la prueba necesita es PostgreSQL real. Las pruebas
  unitarias simulan el cliente HTTP, así que nunca confirman que el servidor acepte ese $expand y devuelva esos campos. La base InMemory no traduce a SQL, así que una
  consulta que Npgsql no sabe traducir, o un orden distinto por la collation de Postgres, pasaría en memoria y fallaría en la base. Collation es la regla de la base para
  comparar y ordenar texto.
  - Qué aporta el navegador: confirma que todo encaja de verdad. El clic en el menú, la dirección del backend que se reemplaza en la imagen, el proxy de nginx, la tabla
  infios-table real pintando datos reales.
  
  Hoy la prueba de navegador también hace un trabajo que no le toca: es la única que comprueba el contrato del servidor (pasos I8–V2), porque falta la capa API.

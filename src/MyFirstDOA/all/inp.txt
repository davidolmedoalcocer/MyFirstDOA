features/csar-stale-lock-cleanup

Necesito implementar una solución sencilla para limpiar stale locks en CSAR.

Estoy trabajando en la rama `features/csar-stale-lock-cleanup`.

Charles indicó que debemos aprovechar los endpoints `GetTaskListDetails` y `GetTeamMgrTaskListDetails` para liberar subtareas que permanezcan bloqueadas después de cierto tiempo.

También consideró razonable utilizar `TASK_TB.UPDATE_DT` como referencia para determinar la antigüedad del bloqueo.

Quiero implementar la siguiente propuesta en mi rama, para revisión de Charles.

### 1. Alcance de la implementación

**API**

En `TranTaskDetailController.cs`, modificar únicamente estos dos endpoints:

- `GetTaskListDetails`
- `GetTeamMgrTaskListDetails`

Cada endpoint deberá llamar a una operación compartida de limpieza antes de ejecutar su lógica actual para obtener la lista.

La limpieza NO debe ejecutarse en otros endpoints del controller.

**SQL Server**

Preparar un stored procedure compartido que:

- Identifique subtareas bloqueadas mediante `TASK_TB.LOCKED_IN = 'Y'`.
- Utilice `TASK_TB.UPDATE_DT` para determinar si superaron el tiempo configurado desde su última actualización.
- Utilice la hora de SQL Server con una referencia temporal consistente.
- Limite los candidatos a las subtareas elegibles para la cola y vista solicitadas.
- Respete las diferencias de filtrado existentes entre Auditoría, Pendientes y Team Manager.
- Vuelva a comprobar las condiciones de bloqueo y antigüedad al ejecutar la actualización.
- Cambie `LOCKED_IN` a `'N'` únicamente para los registros elegibles.

No modificar los stored procedures de listado existentes, salvo que encuentres una dependencia indispensable y la expliques antes de continuar.

**Configuración**

Agregar `TaskLocking:LockTimeoutMinutes` a la configuración de la API utilizando el patrón existente de `appsettings` y opciones tipadas.

No hardcodear el tiempo de expiración. Si necesitas un valor para pruebas, utiliza una configuración local de desarrollo claramente identificada como provisional; no establezcas un plazo de producción sin aprobación.

### 2. Flujo esperado

1. Blazor llama a uno de los dos endpoints.
2. El endpoint ejecuta la operación compartida de limpieza correspondiente a su cola y vista.
3. SQL identifica y libera únicamente los bloqueos que cumplen las condiciones.
4. El endpoint ejecuta el procedimiento de listado existente.
5. La API devuelve los resultados a Blazor.

### 3. Restricciones

- Mantener la implementación lo más sencilla posible.
- No agregar columnas a `TASK_TB`.
- No modificar Blazor inicialmente.
- No implementar nuevos mecanismos de locking.
- No modificar los demás endpoints.
- No ejecutar scripts de desbloqueo sobre bases de datos compartidas.
- No ejecutar UPDATE, DELETE ni procedimientos de escritura contra QA o PROD.
- No hacer commits, push, merge ni deployment automáticamente.
- No modificar componentes legacy.

Antes de modificar el código, inspecciona las firmas reales, las dependencias y los filtros SQL necesarios. No inventes métodos, parámetros ni reglas.

Si descubres que no puedes limitar de forma segura la limpieza a las subtareas elegibles, detén esa parte y explícame el impedimento. No implementes una limpieza global como alternativa.

### 4. Validación

Después de implementar el cambio en los archivos locales:

1. Compila la solución API.
2. Ejecuta las pruebas locales disponibles que no modifiquen datos compartidos.
3. Revisa que solo los dos endpoints indicados invoquen la limpieza.
4. Verifica que los procedimientos de listado sigan funcionando como antes.
5. Prepara pruebas para los límites del timeout y para actualizaciones concurrentes.
6. Documenta el riesgo identificado anteriormente: una pantalla CallUpdate podría intentar guardar después de que su bloqueo haya sido liberado.

Al terminar, muéstrame:

- Archivos modificados.
- Stored procedure nuevo y su contenido.
- Cambios realizados en cada endpoint.
- Configuración agregada.
- Resultado de compilación y pruebas.
- Riesgos o limitaciones pendientes de revisión.

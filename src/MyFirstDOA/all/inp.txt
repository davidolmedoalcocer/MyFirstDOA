features/csar-stale-lock-cleanup

Estoy trabajando en la solución `csar-api` y necesito implementar una mejora de stale-lock cleanup que Charles ya autorizó desarrollar en una feature branch para su revisión.

Rama: `features/csar-stale-lock-cleanup`

**Contexto técnico confirmado en una investigación anterior**

En el proyecto API se identificaron estos endpoints dentro de `TranTaskDetailController.cs`:

- `GetTaskListDetails` → `TranTaskDetailRepo.GetTaskListDetailsAsync` → `TASK_TB_AUDIT_WORK_QUEUE_REQUEST_SSP`
- `GetTeamMgrTaskListDetails` → `TranTaskDetailRepo.GetTeamMgrTaskListDetailsAsync` → `TASK_TB_TEAMMGR_WORK_QUEUE_REQUEST_SSP`

Ambos procedimientos consultan subtareas de `TASK_TB` relacionadas mediante `TRAN_TASK_TB` y excluyen aquellas con `LOCKED_IN = 'Y'`.

Actualmente no ejecutan limpieza automática.

Charles aprobó avanzar con una implementación sencilla que reutilice los campos existentes:

- `TASK_TB.LOCKED_IN`
- `TASK_TB.UPDATE_DT`

La regla propuesta es identificar subtareas bloqueadas cuya última actualización supere un timeout configurable.

Charles también indicó que mañana revisará si existe una lógica de mass unlock que podamos reutilizar.

### Cambios que necesitamos implementar

**1. API — TranTaskDetailController.cs**

Modificar únicamente estas dos acciones:

- `GetTaskListDetails`
- `GetTeamMgrTaskListDetails`

Antes de consultar las listas existentes, cada acción debe invocar una operación compartida de stale-lock cleanup.

No ejecutar la limpieza desde otros endpoints del controller.

**2. SQL Server**

Preparar un script versionable de stored procedure para la limpieza:

- Buscar subtareas con `LOCKED_IN = 'Y'`.
- Evaluar `UPDATE_DT` contra el timeout configurable.
- Utilizar la hora de SQL Server de forma consistente con los datos existentes.
- Limitar los registros a las subtareas elegibles de la cola y vista solicitadas.
- Respetar las diferencias entre Audit, Pending y Team Manager.
- Volver a verificar estado y antigüedad en la operación de desbloqueo.
- Establecer `LOCKED_IN = 'N'` solo en los registros que cumplan las condiciones.

No modificar los stored procedures de listado existentes, salvo que exista una necesidad técnica demostrable.

**3. API — Acceso a datos**

Crear o reutilizar una operación compartida que ejecute el procedimiento de limpieza antes de llamar al repositorio actual.

Revisa primero los patrones disponibles en esta solución.

Si `CSAR.Core` es una dependencia compilada, no modifiques su DLL. Implementa el acceso nuevo siguiendo los patrones disponibles o identifica si es indispensable cambiar el paquete.

**4. Configuración**

Agregar un timeout configurable mediante `TaskLocking:LockTimeoutMinutes`, utilizando el patrón de configuración existente en la API.

No fijar un valor definitivo de producción. Si no hay valor configurado, no debe ejecutarse una limpieza automática con un timeout elegido por ti.

Hey Charles, based on your feedback, I think we can keep the stale locking solution simple by reusing the existing `LOCKED_IN` and `UPDATE_DT` fields in `TASK_TB`, without adding new columns.

Here is my proposed implementation:

**1. API changes**

In `TranTaskDetailController.cs`, update only these two endpoints:

- `GetTaskListDetails`
- `GetTeamMgrTaskListDetails`

Each endpoint would call a shared stale-lock cleanup method before executing its existing task list retrieval logic.

The cleanup would not run for any other endpoints in the controller.

**2. SQL changes**

Create a shared stored procedure to release stale locks using the existing `TASK_TB` fields:

- `LOCKED_IN = 'Y'`
- `UPDATE_DT` older than the configured timeout

The procedure would:
- Use SQL Server time for the comparison.
- Only target eligible transaction tasks for the requested queue and view, respecting the existing Audit and Team Manager filtering rules.
- Recheck the lock conditions during the update before setting `LOCKED_IN = 'N'`.

The existing task list stored procedures would remain unchanged:

- `TASK_TB_AUDIT_WORK_QUEUE_REQUEST_SSP`
- `TASK_TB_TEAMMGR_WORK_QUEUE_REQUEST_SSP`

**3. Configuration**

Add `TaskLocking:LockTimeoutMinutes` to the API's `appsettings`, so the timeout can be configured without hardcoding it.

**4. Execution flow**

1. Blazor calls `GetTaskListDetails` or `GetTeamMgrTaskListDetails`.
2. The corresponding API endpoint executes the shared stale-lock cleanup.
3. SQL releases eligible expired locks.
4. The endpoint executes its existing task list retrieval logic and returns the results.

This approach would require no initial changes to Blazor or the `TASK_TB` schema.

As discussed, `UPDATE_DT` represents the last update to the task rather than a dedicated lock acquisition timestamp, so the timeout would be based on the last recorded update.

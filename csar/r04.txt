Conclusión
No está demostrado que CSARWeb necesite cambios de código para correlacionar logs con APM. La instrumentación automática puede resolverlo y debe ser la primera opción.

APM funciona en QA y Stage; la inyección automática de IDs en Serilog todavía no está confirmada. No propongo agregar middleware mientras esa configuración siga pendiente de comprobar.

HECHOS
1. Qué funciona actualmente
Consulté nuevamente Datadog mediante MCP y confirmé trazas recientes de:

Servicio	Operación observada	Etiquetas
ds-ui-web-csar-qa	aspnet_core.request, GET /health/liveness	env:nonprod, version:2026.1104.2
ds-ui-web-csar-stage	aspnet_core.request, GET /health/liveness	env:nonprod, version:2026.1104.2
También encontré una traza de QA para GET /_blazor, con respuesta HTTP 101, correspondiente a una conexión WebSocket.

Esto demuestra que llegan trazas del proceso .NET. No demuestra que DD_LOGS_INJECTION esté habilitada ni cómo se instaló el tracer.

2. Qué configura el código de CSARWeb
En Program.cs:

Se accede a Tracer.Instance.
Serilog se integra con el host.
Se conserva .Enrich.FromLogContext().
Se agrega un Correlation ID mediante el header CorrelationID.
No se configura explícitamente LogsInjectionEnabled.
No se agregan manualmente dd.trace_id ni dd.span_id.
No encontré creación explícita de spans de Datadog para operaciones de la UI.
Acceder a Tracer.Instance no instala por sí solo la auto-instrumentación necesaria para inyectar IDs en Serilog.

Además, el identificador llamado TraceId de LoggingHandler.cs es un valor aleatorio de seis caracteres enviado como X-Trace-ID: no es el identificador de una traza de Datadog.

Ese handler está registrado en DI, pero no encontré su conexión a un cliente mediante AddHttpMessageHandler. CsarApiProvider.cs crea su propio HttpClient. Por tanto, ese handler no demuestra correlación de las llamadas actuales.

3. Configuraciones de despliegue disponibles
En los archivos revisados no encontré definiciones explícitas de:

DD_LOGS_INJECTION
DD_SERVICE
DD_ENV
DD_VERSION
Variables de activación del profiler de .NET.
El Dockerfile usa una imagen base corporativa y arranca el proceso .NET, pero no instala ni configura Datadog explícitamente.

El archivo DS.UI.Web.CSAR.k8s.yml, pese a su nombre, es una pipeline de construcción y publicación de imagen, no el manifiesto efectivo del Deployment. Referencia plantillas externas.

No dispongo de evidencia de la configuración efectiva del clúster, del contenido de la imagen base ni de posibles modificaciones realizadas por un admission controller.

4. Qué admite la inyección automática
Según la documentación oficial de Datadog:

Serilog admite inyección automática.
Desde el tracer 2.0.1, requiere auto-instrumentación.
Desde el tracer 3.24.0, DD_LOGS_INJECTION está habilitada por defecto.
Debe verificarse la configuración de servicio, ambiente y versión.
La correlación requiere una traza activa cuando se escribe el log y que Datadog reconozca su identificador.
CSARWeb referencia Datadog.Trace 3.50.0. Ese valor predeterminado es favorable, pero no prueba la versión del tracer cargado en producción ni descarta una desactivación explícita o remota.

5. Cómo lo hace CSARApi
CSARApi tiene enriquecimiento explícito, no solamente una expectativa de inyección automática:

ExceptionHandlingMiddleware.cs abre un BeginScope con dd.trace_id y dd.span_id, obtenidos de CorrelationIdentifier.
Program.cs conserva esos campos mediante FromLogContext.
CorrelationIdMiddleware.cs administra X-Correlation-ID, que es un identificador de soporte separado del trace ID.
El scope no crea una traza: necesita que el tracer ya tenga contexto activo.

En esta revisión no recuperé los logs de CSARApi previamente observados con la consulta por Application; por ello, esta comparación se sustenta en el código actual, no en una nueva comprobación de esos logs.

INFERENCIAS
6. Solución más sencilla que preserve el comportamiento actual
Primera opción: aprovechar la instrumentación automática, sin modificar código.

Resultado de la comprobación	Acción mínima
Inyección habilitada y IDs presentes en el JSON	Ningún cambio adicional en CSARWeb
Auto-instrumentación activa, pero inyección deshabilitada	Corregir la configuración del tracer en el despliegue o su configuración remota
IDs presentes, pero Datadog no los reconoce	Ajustar el procesamiento/remapeo en Datadog
No hay traza activa durante una operación Blazor	Investigar esa operación; activar inyección no crea una traza inexistente
No copiaría el middleware de excepciones de CSARApi: también modifica respuestas HTTP y registra errores mediante otros mecanismos. No es necesario para habilitar la integración automática y podría alterar el comportamiento de CSARWeb.

7. Archivos afectados, únicamente si resulta necesario
Por ahora, ningún archivo adicional del repositorio está justificado.

Si falta configuración, el cambio correspondería al manifiesto, valores Helm o mecanismo de instrumentación que realmente gobierne el despliegue, todavía no identificado. No asignaría ese cambio a la pipeline revisada ni a los archivos de configuración de Serilog sin evidencia.

Si los IDs llegan correctamente, pero falla el enlace, el cambio sería en el pipeline de logs de Datadog, no en CSARWeb.

8. HTTP frente a Blazor Server
Solicitud HTTP tradicional	Operación dentro de un circuito Blazor
Tiene inicio y fin de solicitud definidos	Varias acciones comparten una conexión SignalR
Los logs ejecutados dentro de la traza activa pueden recibir sus IDs automáticamente	Una acción de componente no implica una nueva solicitud HTTP ni una nueva traza
La relación solicitud–log suele ser directa	Puede existir contexto de conexión, de una llamada saliente o ninguno, según la ejecución
Tener una traza de /_blazor no garantiza que cada clic, renderizado o excepción del circuito conserve ese contexto. Tampoco garantiza una traza independiente por acción.

CSARWeb ya incluye un ErrorBoundary en MainLayout.razor. Su existencia permite manejar ciertos errores de renderizado, pero no demuestra correlación APM.

PENDIENTES DE VERIFICAR
9. Comprobaciones necesarias antes de decidir cambios
Tracer efectivo: versión cargada y mecanismo de auto-instrumentación.
Configuración efectiva: DD_LOGS_INJECTION, servicio, ambiente y versión, incluyendo overrides remotos.
Integración Serilog: confirmar que no esté deshabilitada.
Contexto activo: comprobarlo tanto para HTTP como para una operación real del circuito.
Procesamiento de logs: confirmar que los IDs del JSON se reconozcan como trace ID y span ID.
La documentación de configuración de .NET indica que puede consultarse la configuración efectiva en APM → servicio → Service Config → SDK Configuration. No pude obtener esa información mediante las operaciones disponibles del MCP.

10. Cómo validar posteriormente en Datadog
Cuando se autorice una validación del despliegue que incluya la Etapa A:

Confirmar que se está observando la versión nueva, no los logs anteriores.
Elegir un log emitido durante una solicitud HTTP trazada.
Inspeccionar el JSON y verificar identificadores de traza y span no vacíos ni cero.
Abrir la traza desde el log y comprobar servicio, operación y tiempos.
Repetirlo con una acción de Blazor y una llamada a CSARApi.
Si falla, distinguir:
Sin IDs: configuración de inyección o ausencia de contexto.
Con IDs, sin enlace: remapeo o disponibilidad de la traza.
Solo falla en Blazor: investigar el contexto de esa operación, no agregar middleware HTTP por defecto.
La traza debe estar disponible según el muestreo y la retención; un ID en un log no garantiza que la traza haya sido conservada.

Decisión recomendada: verificar primero la configuración efectiva y la inyección automática. Todavía no hay fundamento para agregar código de correlación.

No modifiqué archivos, no ejecuté la aplicación, no desplegué ni hice commits. El estado Git conserva únicamente los dos cambios de la Etapa A.
